O que é uma Spec?

No Cypress, uma spec é um arquivo que contém testes automatizados relacionados a determinado comportamento ou funcionalidade.

Normalmente, as specs ficam dentro do diretório cypress/e2e. 

cypress/

└── e2e/

├── login.cy.js
├── cadastro.cy.js
└── produtos.cy.js

Cada arquivo pode representar uma funcionalidade, fluxo ou conjunto de cenários relacionados.

📄 Spec → arquivo que contém os testes.

🧪 Teste → cenário que valida um comportamento.

🗂️ Grupo → conjunto de testes relacionados.

1. Estrutura básica de uma Spec

Uma spec simples pode possuir um agrupamento describe e um ou mais testes utilizando it. 

describe('Login', () => {

it('deve realizar login com sucesso', () => {

    cy.visit('/login')

    cy.get('[data-cy="email"]')
        .type('usuario@email.com')

    cy.get('[data-cy="senha"]')
        .type('123456')

    cy.get('[data-cy="entrar"]')
        .click()

})

})

Nesse exemplo temos dois elementos principais:

🗂️

describe()

Agrupa testes que possuem uma relação entre si.

🧪

it()

Representa um caso de teste específico.

2. Utilizando describe()

O describe() é utilizado para criar um agrupamento de testes. 

describe('Login', () => {

// testes relacionados ao login

})

Podemos utilizar o nome da funcionalidade como identificação do grupo.

Por exemplo: 

describe('Cadastro de usuário', () => {

})

describe('Login de usuário', () => {

})

describe('Produtos', () => {

})
Boa prática:

Utilize nomes que deixem claro qual funcionalidade ou comportamento está sendo testado.

3. Utilizando it()

O it() representa um caso de teste.

Dentro dele colocamos as ações e validações que devem ser executadas. 

it('deve exibir a página inicial', () => {

cy.visit('/')

cy.get('h1')
    .should('be.visible')

})

Podemos criar vários testes dentro de um mesmo describe(). 

describe('Página inicial', () => {

it('deve carregar a página', () => {

    cy.visit('/')

})

it('deve exibir o título', () => {

    cy.visit('/')

    cy.get('h1')
        .should('be.visible')

})

})

4. Relação entre describe() e it()

Podemos pensar no describe() como um grupo e no it() como um teste pertencente a esse grupo.

🗂️ describe → funcionalidade.

🧪 it → comportamento que será validado.

Por exemplo: 

describe('Login', () => {

it('deve permitir login válido', () => {

})

it('deve impedir login com senha inválida', () => {

})

it('deve exibir mensagem de erro', () => {

})

})

Dessa forma, conseguimos organizar vários cenários relacionados à mesma funcionalidade.

5. Utilizando context()

O context() também pode ser utilizado para organizar testes relacionados a uma determinada situação ou contexto. 

describe('Login', () => {

context('quando o usuário informa dados válidos', () => {

    it('deve realizar login', () => {

    })

})

})

Podemos criar diferentes contextos dentro de uma mesma funcionalidade. 

describe('Login', () => {

context('com dados válidos', () => {

    it('deve realizar login', () => {

    })

})

context('com dados inválidos', () => {

    it('deve exibir mensagem de erro', () => {

    })

})

})
Importante:

O context() é uma forma de organizar semanticamente os testes. Ele não cria uma execução especial diferente do describe().

6. Organizando cenários com context()

Imagine que estamos testando uma tela de login. Podemos separar os cenários de acordo com os dados utilizados. 

describe('Login', () => {

context('usuário válido', () => {

    it('deve acessar o sistema', () => {

        cy.visit('/login')

        // teste

    })

})

context('usuário inválido', () => {

    it('deve impedir o acesso', () => {

        cy.visit('/login')

        // teste

    })

})

})

Essa estrutura facilita a leitura da spec e ajuda a identificar rapidamente qual cenário está sendo validado.

7. O que são Hooks?

Hooks são funções utilizadas para executar determinadas ações antes ou depois dos testes.

Os principais hooks do Cypress são:

⏮️

before()

Executado uma vez antes de todos os testes do grupo.

🔄

beforeEach()

Executado antes de cada teste.

🔚

after()

Executado uma vez depois de todos os testes do grupo.

🔁

afterEach()

Executado depois de cada teste.

8. Utilizando before()

O before() é executado uma vez antes dos testes pertencentes ao grupo. 

describe('Produtos', () => {

before(() => {

    cy.visit('/produtos')

})

it('deve exibir os produtos', () => {

    cy.get('.produto')
        .should('be.visible')

})

it('deve exibir o título', () => {

    cy.get('h1')
        .should('contain', 'Produtos')

})

})
Atenção:

O before() é executado uma vez por execução do grupo de testes. Ele não é repetido automaticamente antes de cada teste.

9. Utilizando beforeEach()

O beforeEach() é executado antes de cada teste. 

describe('Login', () => {

beforeEach(() => {

    cy.visit('/login')

})

it('deve exibir o formulário', () => {

    cy.get('form')
        .should('be.visible')

})

it('deve exibir o campo de email', () => {

    cy.get('input[type="email"]')
        .should('be.visible')

})

})

Nesse exemplo, a página de login será acessada antes de cada teste.

🔄 beforeEach() → executa novamente antes de cada teste.

10. Utilizando after()

O after() é executado uma vez depois que todos os testes do grupo forem concluídos. 

describe('Cadastro', () => {

after(() => {

    cy.log('Finalizando testes de cadastro')

})

it('deve permitir cadastro', () => {

    // teste

})

it('deve validar email', () => {

    // teste

})

})

O hook será executado depois dos testes pertencentes ao grupo.

11. Utilizando afterEach()

O afterEach() é executado depois de cada teste. 

describe('Produtos', () => {

afterEach(() => {

    cy.log('Teste finalizado')

})

it('deve listar produtos', () => {

    // teste

})

it('deve permitir adicionar produto', () => {

    // teste

})

})

🔁 afterEach() → executa depois de cada teste.

12. Ordem de execução

Quando utilizamos hooks, é importante entender a ordem em que eles são executados. 

before()

beforeEach()

it()

afterEach()

beforeEach()

it()

afterEach()

after()

Considerando dois testes dentro de um grupo, temos aproximadamente esta sequência:

1️⃣ before()

2️⃣ beforeEach()

3️⃣ Primeiro teste

4️⃣ afterEach()

5️⃣ beforeEach()

6️⃣ Segundo teste

7️⃣ afterEach()

8️⃣ after()

13. Construindo uma Spec completa

Agora podemos combinar describe, context, it e beforeEach em uma mesma spec. 

describe('Login', () => {

beforeEach(() => {

    cy.visit('/login')

})

context('com dados válidos', () => {

    it('deve realizar login com sucesso', () => {

        cy.get('[data-cy="email"]')
            .type('usuario@email.com')

        cy.get('[data-cy="senha"]')
            .type('123456')

        cy.get('[data-cy="entrar"]')
            .click()

    })

})

context('com dados inválidos', () => {

    it('deve exibir mensagem de erro', () => {

        cy.get('[data-cy="email"]')
            .type('email-invalido')

        cy.get('[data-cy="senha"]')
            .type('senha-incorreta')

        cy.get('[data-cy="entrar"]')
            .click()

        cy.get('.mensagem-erro')
            .should('be.visible')

    })

})

})

Essa estrutura já permite criar suítes de testes organizadas e fáceis de compreender.

14. Agrupando testes

Podemos criar grupos dentro de outros grupos quando isso fizer sentido para representar a estrutura funcional da aplicação. 

describe('E-commerce', () => {

describe('Produtos', () => {

    it('deve listar produtos', () => {

    })

})

describe('Carrinho', () => {

    it('deve adicionar produto', () => {

    })

})

})
Boa prática:

Evite criar muitos níveis de agrupamento. A estrutura deve facilitar a leitura, e não tornar o teste mais difícil de compreender.

15. Como escrever bons nomes para os testes

O nome do teste deve explicar claramente qual comportamento está sendo validado.

❌

Nome pouco descritivo

teste login

✅

Nome descritivo

deve realizar login com credenciais válidas

Um bom nome ajuda a entender rapidamente o objetivo do teste quando ele passa ou falha.

16. Evitando dependência entre testes

Cada teste deve ser construído de forma que possa ser executado de maneira independente sempre que possível.

Evite criar uma situação em que um teste dependa obrigatoriamente do resultado de outro teste. 

it('deve criar usuário', () => {

// cria usuário

})

it('deve editar usuário', () => {

// não deve depender da execução anterior

})
Boa prática:

Cada teste deve preparar o estado necessário para validar seu próprio comportamento.

17. Controle de execução dos testes

Durante o desenvolvimento, o Cypress permite controlar temporariamente quais testes serão executados.

Podemos utilizar .skip() para ignorar um teste. 

it.skip('teste temporariamente ignorado', () => {

// teste

})

Também existe .only(), que pode ser utilizada temporariamente para executar apenas determinado teste ou grupo. 

it.only('executar somente este teste', () => {

// teste

})
Atenção:

O uso de .only() deve ser temporário. Antes de enviar o código para o repositório, verifique se nenhum teste ficou acidentalmente marcado como only.

18. Organização recomendada

Uma spec pode ser organizada seguindo uma estrutura semelhante a esta: 

describe('Funcionalidade', () => {

before(() => {

    // preparação geral

})

beforeEach(() => {

    // preparação antes de cada teste

})

context('cenário 1', () => {

    it('deve realizar comportamento esperado', () => {

        // teste

    })

})

context('cenário 2', () => {

    it('deve apresentar comportamento esperado', () => {

        // teste

    })

})

afterEach(() => {

    // limpeza após cada teste

})

after(() => {

    // finalização

})

})

Nem toda spec precisa utilizar todos esses elementos. Utilize apenas aqueles que realmente ajudam na organização do teste.

Erros comuns na estrutura de uma Spec

❌

Testes sem organização

Colocar muitos testes diferentes no mesmo arquivo sem agrupamento adequado.

❌

Nomes genéricos

Utilizar nomes que não explicam o comportamento validado pelo teste.

❌

Dependência entre testes

Fazer um teste depender obrigatoriamente do resultado de outro.

❌

Uso excessivo de hooks

Colocar muita lógica em hooks e dificultar a compreensão do comportamento de cada teste.

Boas práticas para Specs

🎯

Tenha um objetivo claro

Cada spec deve possuir um propósito relacionado às funcionalidades que está validando.

📝

Use nomes descritivos

Os nomes devem explicar claramente o cenário e o comportamento esperado.

🧩

Organize por contexto

Utilize describe e context para separar cenários relacionados.

🔄

Use hooks com propósito

Utilize hooks para comportamentos realmente compartilhados entre os testes.

🧪

Mantenha os testes independentes

Evite que um teste dependa da execução anterior de outro teste.

🧹

Evite complexidade desnecessária

Uma estrutura simples geralmente é mais fácil de entender e manter.
