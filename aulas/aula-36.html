O que é um Custom Command?

Um Custom Command é um comando personalizado criado pelo projeto para encapsular uma sequência de ações que pode ser reutilizada em diferentes testes.

Em vez de repetir várias linhas de código, podemos criar um único comando responsável por executar determinado comportamento. 

Cypress.Commands.add('login', () => {

    // comandos do login

})

🧩 Custom Command → comportamento reutilizável.

♻️ Reutilização → evita repetir a mesma sequência de comandos.

🧹 Organização → mantém as specs mais simples e legíveis.

1. Onde ficam os Custom Commands?

Os comandos personalizados normalmente são definidos no arquivo: 

cypress/support/commands.js

Uma estrutura comum de projeto pode ser: 

curso-cypress/

├── cypress/
│
├── e2e/
│   └── login.cy.js
│
├── fixtures/
│   └── usuario.json
│
└── support/
    ├── commands.js
    └── e2e.js

├── cypress.config.js
├── package.json
└── package-lock.json

O arquivo commands.js é utilizado para centralizar comandos personalizados que podem ser utilizados pelas specs.

2. Criando nosso primeiro Custom Command

Vamos criar um comando chamado login. 

Cypress.Commands.add('login', () => {

    cy.visit('/login')

})

Depois de criado, podemos utilizar o comando diretamente na spec: 

cy.login()

O comando personalizado passa a fazer parte da API de comandos do projeto.

3. Custom Command com argumentos

Um comando personalizado também pode receber informações como argumentos.

Por exemplo, podemos criar um comando de login que recebe e-mail e senha. 

Cypress.Commands.add(
    'login',
    (email, senha) => {

    cy.visit('/login')

    cy.get('#email')
        .type(email)

    cy.get('#senha')
        .type(senha)

    cy.get('#login')
        .click()

})

Agora podemos chamar o comando informando os valores necessários: 

cy.login(
    'usuario@teste.com',
    '123456'
)
📧

Email

Primeiro argumento recebido pelo comando.

🔑

Senha

Segundo argumento utilizado durante o login.

🔄

Reutilização

O mesmo comando pode ser utilizado com diferentes usuários.

4. Criando um comando de login

Login é um dos exemplos mais comuns de aplicação de Custom Commands.

Sem um comando personalizado, poderíamos ter: 

cy.visit('/login')

cy.get('#email')
    .type('usuario@teste.com')

cy.get('#senha')
    .type('123456')

cy.get('#login')
    .click()

Podemos transformar esse comportamento em um comando: 

Cypress.Commands.add(
    'login',
    (email, senha) => {

    cy.visit('/login')

    cy.get('#email')
        .type(email)

    cy.get('#senha')
        .type(senha)

    cy.get('#login')
        .click()

})

E então utilizar: 

cy.login(
    'usuario@teste.com',
    '123456'
)

O teste fica mais curto porque os detalhes da implementação do login foram encapsulados no Custom Command.

5. Custom Command utilizando fixture

Também podemos combinar Custom Commands com fixtures.

Considere o arquivo: 

{
    "email": "usuario@teste.com",
    "senha": "123456"
}

Podemos criar um comando que recebe os dados: 

Cypress.Commands.add(
    'login',
    (usuario) => {

    cy.visit('/login')

    cy.get('#email')
        .type(usuario.email)

    cy.get('#senha')
        .type(usuario.senha)

    cy.get('#login')
        .click()

})

Na spec: 

cy.fixture('usuario.json')
    .then((usuario) => {

        cy.login(usuario)

    })

Dessa forma, o fixture fica responsável pelos dados enquanto o Custom Command fica responsável pelo comportamento.

6. Criando comandos para elementos

Custom Commands também podem encapsular ações comuns realizadas em elementos.

Por exemplo: 

Cypress.Commands.add(
    'preencherEmail',
    (email) => {

    cy.get('[data-testid="email"]')
        .clear()
        .type(email)

})

Utilização: 

cy.preencherEmail(
    'usuario@teste.com'
)

Esse tipo de comando pode ser útil quando determinada interação aparece repetidamente em diferentes cenários.

7. Comandos encadeáveis

Alguns Custom Commands podem retornar um elemento para continuar o encadeamento de comandos.

Um exemplo é um comando para localizar um elemento por data-testid. 

Cypress.Commands.add(
    'getByTestId',
    (testId) => {

    return cy.get(
        `[data-testid="${testId}"]`
    )

})

Agora podemos utilizar: 

cy.getByTestId('email')
    .should('be.visible')

Ou: 

cy.getByTestId('email')
    .type('usuario@teste.com')

Quando um comando retorna um objeto da cadeia do Cypress, outros comandos podem continuar sendo encadeados.

8. Custom Commands com validações

Um Custom Command também pode encapsular uma validação utilizada frequentemente. 

Cypress.Commands.add(
    'validarLogin',
    () => {

    cy.url()
        .should('include', 'dashboard')

})

No teste: 

cy.login(
    'usuario@teste.com',
    '123456'
)

cy.validarLogin()
🧪

Ação

O comando pode executar as ações necessárias para determinado comportamento.

✅

Validação

O comando também pode centralizar uma validação recorrente.

♻️

Reutilização

A mesma lógica pode ser utilizada por vários testes.

9. Custom Command x função JavaScript

Nem toda lógica reutilizável precisa ser transformada em um Custom Command.

Uma função JavaScript pode ser suficiente quando não precisamos interagir diretamente com a cadeia de comandos do Cypress. 

function gerarNome() {

    return 'Maria'

}

Já um Custom Command é apropriado quando queremos adicionar um comportamento à API do Cypress. 

Cypress.Commands.add(
    'login',
    (email, senha) => {

    cy.visit('/login')

    cy.get('#email')
        .type(email)

    cy.get('#senha')
        .type(senha)

})
Importante:

Custom Commands devem representar comportamentos úteis e reutilizáveis. Criar comandos para toda e qualquer pequena ação pode tornar o projeto mais difícil de entender.

10. Organizando os Custom Commands

Conforme o projeto cresce, podemos ter vários comandos personalizados. 

cypress/

└── support/

    ├── commands.js
    └── e2e.js

O arquivo commands.js pode conter comandos relacionados a diferentes funcionalidades: 

Cypress.Commands.add(
    'login',
    (email, senha) => {

    // login

})

Cypress.Commands.add(
    'logout',
    () => {

    // logout

})

Cypress.Commands.add(
    'getByTestId',
    (id) => {

    return cy.get(
        `[data-testid="${id}"]`
    )

})

Em projetos maiores, também é possível dividir comandos por responsabilidade e importar os arquivos necessários.

11. Exemplo completo

Vamos criar um Custom Command de login utilizando dados recebidos como argumentos.

No arquivo commands.js: 

Cypress.Commands.add(
    'login',
    (email, senha) => {

    cy.visit('/login')

    cy.get('[data-testid="email"]')
        .type(email)

    cy.get('[data-testid="senha"]')
        .type(senha)

    cy.get('[data-testid="login"]')
        .click()

})

Na spec: 

describe('Login', () => {

    it('deve realizar login com sucesso', () => {

        cy.login(
            'usuario@teste.com',
            '123456'
        )

        cy.url()
            .should('include', 'dashboard')

    })

})

A spec agora descreve o comportamento esperado sem precisar repetir todos os detalhes da implementação do login.

12. Utilizando objetos como argumentos

Quando um comando possui vários parâmetros, podemos utilizar um objeto para deixar sua chamada mais clara. 

Cypress.Commands.add(
    'login',
    ({ email, senha }) => {

    cy.visit('/login')

    cy.get('#email')
        .type(email)

    cy.get('#senha')
        .type(senha)

    cy.get('#login')
        .click()

})

A chamada pode ser feita desta maneira: 

cy.login({

    email: 'usuario@teste.com',

    senha: '123456'

})

Objetos podem tornar comandos com muitos parâmetros mais fáceis de ler e evoluir.

Boas práticas com Custom Commands

🎯

Tenha um propósito claro

Crie comandos para comportamentos que realmente sejam reutilizados no projeto.

🏷️

Use nomes claros

O nome do comando deve indicar claramente o comportamento executado.

♻️

Evite duplicação

Centralize comportamentos repetitivos quando isso realmente melhorar a manutenção.

🧹

Evite abstrações excessivas

Nem toda linha de código precisa ser escondida dentro de um Custom Command.

Erros comuns com Custom Commands

❌

Nome pouco claro

Criar comandos com nomes que não deixam claro qual comportamento será executado.

❌

Comandos gigantes

Criar comandos que realizam muitas responsabilidades diferentes.

❌

Abstração desnecessária

Criar um Custom Command para uma ação simples que já é clara na própria spec.

❌

Dependências ocultas

Criar comandos que dependem de estados ou informações que não ficam evidentes para quem utiliza o comando.

Quando utilizar Custom Commands?

Situação Custom Command? Motivo
Login repetido Sim Comportamento reutilizado em vários testes.
Ação muito simples Nem sempre Pode adicionar abstração desnecessária.
Seleção padronizada por testid Pode ser útil Centraliza uma estratégia de localização.
Fluxo complexo e repetitivo Sim Reduz duplicação entre os testes.
Lógica exclusiva de um teste Geralmente não Não existe reutilização suficiente.
