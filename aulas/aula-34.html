Mock de APIs

Aprenda a simular respostas de APIs utilizando o Cypress para criar testes mais previsíveis, rápidos e independentes de serviços externos.

Objetivos da aula

Na aula anterior, aprendemos a utilizar o cy.intercept() para interceptar requisições HTTP.

Agora vamos utilizar esse conhecimento para criar mocks de APIs e controlar as respostas recebidas pela aplicação durante os testes.

🔀

O que é Mock?

Um mock é uma simulação de um componente real utilizado durante a execução de um teste.

No contexto de APIs, podemos substituir temporariamente a resposta real de um servidor por uma resposta controlada pelo teste. 

Aplicação

        ↓

    Requisição

        ↓

      Mock

        ↓

Resposta simulada

🎭 Mock → simula um comportamento real.

🌐 API real → serviço normalmente utilizado pela aplicação.

🧪 Teste → controla o cenário e valida o comportamento da aplicação.

Por que utilizar mocks?

Durante os testes E2E, a aplicação pode depender de diferentes APIs e serviços externos.

Se esses serviços estiverem indisponíveis ou retornarem dados diferentes, o resultado do teste pode ser afetado.

⚡

Mais velocidade

Evita algumas dependências de serviços externos durante determinados cenários.

🎯

Previsibilidade

O teste recebe exatamente a resposta definida para aquele cenário.

🔧

Controle

Podemos simular diferentes respostas da API.

🚫

Menos dependências

O teste pode ser executado sem depender de determinadas respostas do backend.

1. Criando um mock com cy.intercept()

Podemos utilizar o cy.intercept() para interceptar uma requisição e definir uma resposta estática. 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 200,
        body: {
            usuarios: []
        }
    }
)

Nesse exemplo, qualquer requisição GET para /api/usuarios receberá a resposta definida pelo teste.

A aplicação continua realizando a requisição, mas o Cypress controla a resposta recebida.

2. Criando uma resposta personalizada

Podemos definir um objeto completo como resposta da API. 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 200,
        body: {
            usuarios: [
                {
                    id: 1,
                    nome: 'Maria',
                    email: 'maria@teste.com'
                },
                {
                    id: 2,
                    nome: 'João',
                    email: 'joao@teste.com'
                }
            ]
        }
    }
)

Dessa forma, podemos controlar exatamente quais dados serão apresentados para a aplicação.

3. Utilizando alias com o mock

Podemos atribuir um alias ao intercept para acompanhar a requisição durante o teste. 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 200,
        body: {
            usuarios: []
        }
    }
).as('listarUsuarios')

Depois podemos aguardar a requisição: 

cy.wait('@listarUsuarios')

O alias permite sincronizar o teste com a requisição interceptada.

4. Mock antes do cy.visit()

Em muitos cenários, o intercept deve ser criado antes da aplicação realizar a requisição. 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 200,
        body: {
            usuarios: [
                {
                    id: 1,
                    nome: 'Maria'
                }
            ]
        }
    }
).as('usuarios')

cy.visit('/usuarios')

cy.wait('@usuarios')
Boa prática:

Quando a página realiza uma requisição automaticamente ao ser carregada, configure o intercept antes do cy.visit().

5. Mockando uma API de login

Podemos simular uma resposta de sucesso para uma API de autenticação. 

cy.intercept(
    'POST',
    '/api/login',
    {
        statusCode: 200,
        body: {
            token: 'token-teste',
            usuario: {
                id: 1,
                nome: 'Maria'
            }
        }
    }
).as('login')

cy.visit('/login')

cy.get('#email')
    .type('maria@teste.com')

cy.get('#senha')
    .type('123456')

cy.get('#login')
    .click()

cy.wait('@login')

O teste pode validar o comportamento da interface sem depender da autenticação real do backend.

6. Simulando diferentes status codes

Uma das vantagens dos mocks é poder testar como a aplicação reage a diferentes respostas HTTP. 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 200,
        body: {
            usuarios: []
        }
    }
)

Podemos também simular erros: 

cy.intercept(
    'GET',
    '/api/usuarios',
    {
        statusCode: 500,
        body: {
            mensagem: 'Erro interno do servidor'
        }
    }
)
✅

200

Simula uma resposta de sucesso.

🔐

401

Pode simular uma requisição não autenticada.

🚫

403

Pode simular acesso não autorizado.

💥

500

Pode simular um erro interno do servidor.

7. Testando mensagens de erro

Podemos utilizar um mock para verificar se a interface apresenta corretamente uma mensagem quando a API falha. 

cy.intercept(
    'GET',
    '/api/produtos',
    {
        statusCode: 500,
        body: {
            mensagem: 'Não foi possível carregar os produtos'
        }
    }
).as('produtos')

cy.visit('/produtos')

cy.wait('@produtos')

cy.get('[data-testid="mensagem-erro"]')
    .should(
        'contain',
        'Não foi possível carregar os produtos'
    )

Esse tipo de cenário permite validar comportamentos de erro que podem ser difíceis de reproduzir utilizando somente a API real.

8. Simulando uma lista vazia

Também podemos testar como a aplicação se comporta quando uma API retorna uma lista sem registros. 

cy.intercept(
    'GET',
    '/api/produtos',
    {
        statusCode: 200,
        body: {
            produtos: []
        }
    }
).as('produtos')

cy.visit('/produtos')

cy.wait('@produtos')

cy.get('[data-testid="lista-vazia"]')
    .should('be.visible')

Esse cenário é conhecido como empty state e é importante para validar o comportamento da interface quando não existem dados.

9. Utilizando fixtures como resposta do mock

Também podemos combinar fixtures com cy.intercept().

Imagine um arquivo: 

cypress/fixtures/produtos.json

Podemos utilizá-lo como resposta: 

cy.intercept(
    'GET',
    '/api/produtos',
    {
        fixture: 'produtos.json'
    }
).as('produtos')

Dessa forma, os dados do mock ficam separados da lógica do teste e podem ser reutilizados.

10. Alterando a resposta durante o teste

Em alguns cenários podemos utilizar uma função para trabalhar com a requisição interceptada. 

cy.intercept(
    'GET',
    '/api/usuarios',
    (request) => {

        request.reply({
            statusCode: 200,
            body: {
                usuarios: [
                    {
                        id: 1,
                        nome: 'Maria'
                    }
                ]
            }
        })

    }
)

O callback recebe informações sobre a requisição e permite controlar a resposta utilizando request.reply().

Essa abordagem é útil quando o cenário exige um controle mais específico sobre a requisição ou a resposta.

11. Inspecionando a requisição

O objeto de requisição também pode ser utilizado para analisar informações enviadas pela aplicação. 

cy.intercept(
    'POST',
    '/api/login',
    (request) => {

        cy.log(request.body)

        request.reply({
            statusCode: 200,
            body: {
                sucesso: true
            }
        })

    }
)

O request.body, por exemplo, pode representar os dados enviados no corpo da requisição.

12. Criando diferentes cenários

Uma aplicação pode apresentar comportamentos diferentes dependendo da resposta da API.

Cenário Status Objetivo
Sucesso 200 Validar o fluxo normal.
Sem dados 200 Validar lista vazia.
Não autenticado 401 Validar comportamento de autenticação.
Acesso negado 403 Validar mensagens de autorização.
Erro interno 500 Validar tratamento de falhas.

13. Mock x API real

Mocks e testes utilizando APIs reais possuem objetivos diferentes.

🎭

Mock

Permite controlar a resposta e criar cenários específicos.

🌐

API real

Permite verificar a integração com o serviço real.

🧪

Estratégia

Uma suíte pode combinar diferentes tipos de testes de acordo com seus objetivos.

Mockar uma API não significa que a integração real deixou de precisar ser testada.

O mock é uma ferramenta para controlar cenários específicos durante os testes.

Boas práticas ao criar mocks

🎯

Mocke apenas o necessário

Utilize mocks quando eles realmente contribuírem para o cenário de teste.

📁

Organize os dados

Utilize fixtures quando as respostas forem grandes ou reutilizadas.

🏷️

Utilize aliases

Dê nomes claros aos intercepts para facilitar a leitura dos testes.

⚠️

Teste cenários de erro

Simule falhas para verificar como a aplicação reage.

Erros comuns ao utilizar mocks

❌

Interceptar depois da requisição

Criar o intercept depois que a aplicação já realizou a requisição.

❌

URL incorreta

Utilizar uma URL diferente daquela realmente chamada pela aplicação.

❌

Resposta incompatível

Retornar uma estrutura de dados diferente daquela esperada pelo frontend.

❌

Testar somente o mock

Esquecer que a integração real também possui cenários que precisam ser avaliados.

14. Exemplo completo

Vamos criar um teste que simula uma API de produtos retornando dois registros. 

describe('Produtos', () => {

    it('deve exibir os produtos retornados pela API', () => {

        cy.intercept(
            'GET',
            '/api/produtos',
            {
                statusCode: 200,
                body: {
                    produtos: [
                        {
                            id: 1,
                            nome: 'Notebook',
                            preco: 3500
                        },
                        {
                            id: 2,
                            nome: 'Mouse',
                            preco: 150
                        }
                    ]
                }
            }
        ).as('produtos')

        cy.visit('/produtos')

        cy.wait('@produtos')

        cy.get('[data-testid="produto"]')
            .should('have.length', 2)

        cy.contains('Notebook')
            .should('be.visible')

        cy.contains('Mouse')
            .should('be.visible')

    })

})

O teste controla a resposta da API e depois valida como a interface apresenta os dados.

Fluxo de um teste utilizando Mock 

1. Criar o intercept
        ↓
2. Definir a resposta
        ↓
3. Abrir a aplicação
        ↓
4. Aplicação realiza a requisição
        ↓
5. Cypress intercepta
        ↓
6. Cypress retorna o mock
        ↓
7. Aplicação recebe os dados
        ↓
8. Teste valida o comportamento

O principal objetivo é controlar o cenário de forma previsível para validar o comportamento da aplicação.
