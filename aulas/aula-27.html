O que é massa de testes?

Massa de testes é o conjunto de dados utilizado para executar determinados cenários durante os testes.

Esses dados podem representar usuários, produtos, pedidos, endereços, informações financeiras, configurações ou qualquer outro dado necessário para a execução de um cenário.

🧪 Massa de testes → conjunto de dados utilizados na execução dos cenários.

🎯 Cenário → situação que queremos validar.

📋 Dados → informações necessárias para executar o cenário.

1. Exemplo de massa de testes

Imagine que precisamos testar uma tela de cadastro de usuários.

Podemos criar diferentes conjuntos de dados:

Usuário Email Senha Cenário
João joao@teste.com 123456 Cadastro válido
Maria maria@teste.com 123456 Cadastro válido
Carlos email-invalido 123456 Email inválido

Cada registro representa uma possibilidade diferente de execução.

2. Dados positivos e negativos

Uma boa massa de testes normalmente precisa considerar diferentes tipos de cenários.

✅

Cenários positivos

Utilizam dados válidos e esperam que a operação seja concluída com sucesso.

❌

Cenários negativos

Utilizam dados inválidos para validar o comportamento esperado da aplicação.

⚠️

Casos limite

Utilizam valores próximos dos limites definidos pelas regras da aplicação.

3. Organizando uma massa de testes

Podemos organizar os dados em diferentes arquivos dentro da pasta de fixtures. 

cypress/

├── e2e/
│
├── fixtures/
│ ├── usuarios-validos.json
│ ├── usuarios-invalidos.json
│ ├── produtos.json
│ └── pedidos.json
│
└── support/

Essa estrutura permite identificar rapidamente qual conjunto de dados cada arquivo representa.

📁 usuarios-validos.json → dados para cenários de sucesso.

📁 usuarios-invalidos.json → dados para cenários de validação.

📁 produtos.json → dados relacionados a produtos.

4. Criando uma massa de usuários

Podemos criar um arquivo contendo vários usuários. 

[
{
    "nome": "João",
    "email": "joao@teste.com",
    "senha": "123456"
},

{
    "nome": "Maria",
    "email": "maria@teste.com",
    "senha": "654321"
},

{
    "nome": "Carlos",
    "email": "carlos@teste.com",
    "senha": "abc123"
}

]

Agora temos três registros disponíveis para os testes.

5. Carregando uma massa de dados

Podemos carregar o arquivo utilizando cy.fixture(). 

cy.fixture('usuarios-validos')
.as('usuarios')

Depois podemos utilizar os dados durante o teste. 

cy.get('@usuarios')
Importante:

Uma fixture contendo um array representa vários registros. O teste precisa definir como esses registros serão utilizados.

6. Percorrendo uma massa de dados

Quando temos vários registros, podemos percorrer os dados utilizando estruturas do JavaScript. 

cy.fixture('usuarios-validos')
.then((usuarios) => {

    usuarios.forEach((usuario) => {

        cy.log(usuario.nome)

    })

})

Nesse exemplo, o forEach() percorre cada usuário presente na massa de dados.

📋 usuarios → array carregado da fixture.

👤 usuario → registro atual durante a iteração.

🔄 forEach() → percorre os registros.

7. Utilizando dados em um teste

Podemos utilizar cada usuário para executar uma ação dentro da aplicação. 

cy.fixture('usuarios-validos')
.then((usuarios) => {

    usuarios.forEach((usuario) => {

        cy.visit('/login')

        cy.get('[data-testid="email"]')
            .clear()
            .type(usuario.email)

        cy.get('[data-testid="senha"]')
            .clear()
            .type(usuario.senha)

        cy.get('[data-testid="login"]')
            .click()

    })

})

Esse exemplo demonstra uma possibilidade de utilização de vários registros dentro de um fluxo.

Atenção:

Em projetos reais, é importante avaliar se cada registro deve ser executado no mesmo teste ou se é mais adequado separar os cenários.

8. Criando massa para cenários negativos

Podemos criar dados específicos para validar mensagens de erro. 

[
{
    "email": "email-invalido",
    "senha": "123456",
    "mensagem": "Email inválido"
},

{
    "email": "usuario@teste.com",
    "senha": "",
    "mensagem": "Senha obrigatória"
},

{
    "email": "",
    "senha": "123456",
    "mensagem": "Email obrigatório"
}

]

Dessa maneira, além dos dados de entrada, podemos armazenar também o resultado esperado.

9. Testes orientados a dados

Quando um mesmo fluxo precisa ser executado com diferentes conjuntos de dados, podemos aplicar uma abordagem orientada a dados. 

const usuarios = [

{
    email: 'joao@teste.com',
    senha: '123456'
},

{
    email: 'maria@teste.com',
    senha: '654321'
}

]

O mesmo fluxo pode ser utilizado para diferentes entradas.

🔄 Mesmo comportamento → executado várias vezes.

📋 Dados diferentes → cada execução utiliza uma entrada.

🎯 Objetivo → validar o comportamento para diferentes combinações de dados.

10. Armazenando resultado esperado

Uma massa de testes pode armazenar não apenas os dados de entrada, mas também informações sobre o resultado esperado. 

{
"email": "email-invalido",
"senha": "123456",
"resultadoEsperado": {
    "sucesso": false,
    "mensagem": "Email inválido"
}

}

Isso permite que o próprio conjunto de dados descreva parte do cenário que será validado.

11. Massa de testes para produtos

O conceito também pode ser utilizado em outros contextos além de usuários. 

[
{
    "nome": "Notebook",
    "preco": 3500,
    "categoria": "Eletrônicos"
},

{
    "nome": "Mouse",
    "preco": 100,
    "categoria": "Periféricos"
}

]

Essa estrutura pode ser utilizada para validar listagens, filtros, detalhes de produtos ou operações de compra.

12. Testando casos limite

Uma massa de testes também pode conter valores próximos aos limites definidos pelas regras da aplicação.

Por exemplo, se um campo aceita até 50 caracteres, podemos criar dados como: 

{
"nomeValido": "Nome com tamanho permitido",
"nomeMuitoGrande": "Nome que ultrapassa o limite definido..."

}
0️⃣

Valor mínimo

Verificar o comportamento no menor valor permitido.

🔢

Valor máximo

Verificar o comportamento no maior valor permitido.

⚠️

Valor acima do limite

Verificar como a aplicação trata valores que ultrapassam a regra.

13. Massa de testes e isolamento

Os testes devem ser planejados de maneira que um cenário não dependa indevidamente do resultado de outro.

Exemplo:

Se um teste altera o email de um usuário e o próximo teste depende daquele mesmo registro, podemos criar uma dependência entre os testes.

Sempre que possível, cada cenário deve possuir os dados necessários para sua própria execução.

O objetivo é tornar os testes mais previsíveis e facilitar a identificação de falhas.

14. Massa estática e dados dinâmicos

É importante diferenciar dados estáticos de dados que precisam ser gerados dinamicamente.

Tipo Exemplo Uso
Estático Produto conhecido Fixture
Dinâmico Email único Gerado durante o teste
Persistente Registro criado no sistema API ou banco de dados

A estratégia deve ser escolhida de acordo com a necessidade do cenário.

15. Organização de uma massa maior

Em projetos maiores, podemos separar os dados por domínio e finalidade. 

cypress/

├── fixtures/
│
├── usuarios/
│ ├── validos.json
│ └── invalidos.json
│
├── produtos/
│ ├── eletronicos.json
│ └── perifericos.json
│
├── pedidos/
│ ├── aprovados.json
│ └── cancelados.json
│
└── enderecos/
├── validos.json
└── invalidos.json

A estrutura deve ser adaptada ao tamanho e às necessidades do projeto.

Não existe uma única organização obrigatória para todos os projetos.

Boas práticas para massa de testes

🎯

Dados relevantes

Crie dados que representem cenários reais e úteis para os testes.

🏷️

Nomes claros

Utilize nomes que indiquem claramente o objetivo dos dados.

♻️

Evite duplicação

Não mantenha várias cópias desnecessárias do mesmo conjunto de dados.

🔐

Proteja dados sensíveis

Nunca utilize informações reais e sensíveis sem uma estratégia adequada de proteção.

🧹

Mantenha os dados atualizados

Remova ou atualize registros que deixaram de representar a aplicação.

🧪

Cubra diferentes cenários

Considere casos positivos, negativos e situações limite.

Erros comuns

❌

Usar sempre os mesmos dados

Testar somente um cenário e deixar de explorar outras combinações relevantes.

❌

Misturar dados de cenários

Criar arquivos que combinam informações sem uma finalidade clara.

❌

Dados dependentes entre testes

Fazer um teste depender de alterações realizadas por outro teste.

❌

Dados sensíveis no repositório

Armazenar credenciais reais, tokens ou informações privadas na massa de testes.

Fluxo para criar uma massa de testes

🔎 1. Identifique o cenário → descubra o que precisa ser validado.

📋 2. Identifique os dados → determine quais informações o cenário precisa.

🧪 3. Crie os registros → prepare dados positivos, negativos e limites.

📁 4. Organize os arquivos → mantenha os dados separados de forma clara.

♻️ 5. Utilize nos testes → carregue os dados e execute os cenários.

🧹 6. Mantenha os dados → atualize a massa conforme a aplicação evoluir.
