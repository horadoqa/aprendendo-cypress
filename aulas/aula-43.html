O que é GitHub Actions?

O GitHub Actions é um recurso do GitHub utilizado para automatizar tarefas relacionadas ao desenvolvimento de software.

Ele permite criar workflows capazes de executar comandos automaticamente quando determinados eventos acontecem no repositório.

Entre as tarefas que podem ser automatizadas estão:

🧪

Testes

Executar testes automatizados a cada alteração do código.

🔍

Validações

Executar lint, análise estática e outras verificações.

📦

Build

Construir aplicações e gerar artefatos.

🚀

Deploy

Automatizar etapas de entrega da aplicação.

GitHub Actions permite transformar tarefas que anteriormente eram executadas manualmente em processos automatizados.

1. Conceitos fundamentais

Antes de criar nosso primeiro workflow, precisamos entender alguns conceitos utilizados pelo GitHub Actions.

Conceito Descrição
Workflow Arquivo que define um processo automatizado.
Event Evento responsável por iniciar o workflow.
Job Conjunto de etapas executadas em um ambiente.
Step Uma etapa individual dentro de um job.
Runner Máquina responsável por executar o job.
Action Componente reutilizável utilizado em um workflow.

2. O que é um workflow?

Um workflow é um arquivo que descreve as etapas que devem ser executadas automaticamente pelo GitHub Actions.

Os workflows são armazenados dentro da pasta: 

.github/workflows/

Por exemplo: 

projeto-cypress/

├── .github/
│
│ └── workflows/
│ └── cypress.yml
│
├── cypress/
│
├── cypress.config.js
├── package.json
└── package-lock.json

Os arquivos dentro de .github/workflows/ possuem extensão .yml ou .yaml.

3. Criando nosso primeiro workflow

Vamos criar o arquivo: 

.github/workflows/cypress.yml

Um workflow simples pode começar desta forma: 

name: Cypress Tests

on:
push:

jobs:

cypress:

runs-on: ubuntu-latest

steps:

  - name: Checkout
    uses: actions/checkout@v4

  - name: Setup Node
    uses: actions/setup-node@v4
    with:
      node-version: 20

  - name: Install dependencies
    run: npm ci

  - name: Run Cypress
    run: npx cypress run

Esse arquivo define um processo completo para executar os testes Cypress.

4. Definindo o nome do workflow

A propriedade name define o nome que será exibido na interface do GitHub. 

name: Cypress Tests

Podemos utilizar um nome mais específico: 

name: Testes E2E com Cypress

Utilize nomes claros para facilitar a identificação dos workflows no repositório.

5. Eventos que iniciam o workflow

A propriedade on define os eventos responsáveis por iniciar a execução do workflow.

Um exemplo simples: 

on:

push:

Nesse caso, o workflow será executado quando houver um push no repositório.

Também podemos executar o workflow em pull requests: 

on:

pull_request:

Podemos utilizar os dois eventos: 

on:

push:
pull_request:
📤

push

Executa o workflow após um push no repositório.

🔀

pull_request

Executa o workflow relacionado a uma pull request.

🖱️

workflow_dispatch

Permite iniciar o workflow manualmente pela interface do GitHub.

6. Criando um job

Um workflow pode possuir um ou vários jobs.

Nosso job será responsável por executar os testes Cypress. 

jobs:

cypress:

O nome cypress é um identificador utilizado para esse job.

Um workflow pode possuir diferentes jobs para diferentes responsabilidades, como testes, build e deploy.

7. Escolhendo o runner

O job precisa definir em qual ambiente será executado.

Para isso utilizamos runs-on. 

runs-on: ubuntu-latest

Nesse exemplo, o job utilizará um ambiente Linux disponibilizado pelo GitHub.

🐧

Ubuntu

Ambiente Linux utilizado frequentemente em pipelines de CI.

🪟

Windows

Pode ser utilizado quando o projeto depende de recursos específicos do Windows.

🍎

macOS

Pode ser utilizado para cenários que exigem ambiente macOS.

8. Fazendo checkout do projeto

Antes de executar os testes, o código do repositório precisa estar disponível no runner.

Utilizamos a action oficial de checkout: 

- name: Checkout

uses: actions/checkout@v4

Essa etapa disponibiliza os arquivos do repositório no ambiente em que o job está sendo executado.

Importante:

Sem o checkout, o runner não terá automaticamente o código do projeto disponível para as etapas seguintes.

9. Configurando o Node.js

Como nosso projeto Cypress utiliza Node.js, precisamos preparar o ambiente. 

- name: Setup Node

uses: actions/setup-node@v4
with:
node-version: 20

Dessa forma, o workflow utiliza uma versão específica do Node.js.

Definir explicitamente a versão do Node ajuda a manter o ambiente de execução previsível.

10. Instalando as dependências

Depois de preparar o Node.js, precisamos instalar as dependências do projeto.

Para projetos que possuem package-lock.json, podemos utilizar: 

npm ci

No workflow: 

- name: Install dependencies

run: npm ci

O comando npm ci é especialmente apropriado para ambientes automatizados porque utiliza o lockfile para instalar as dependências definidas pelo projeto.

11. Executando o Cypress

Com as dependências instaladas, podemos executar os testes. 

- name: Run Cypress

run: npx cypress run

O comando executa o Cypress em modo de execução, adequado para ambientes de CI.

Podemos especificar um navegador: 

npx cypress run --browser chrome

Ou executar uma determinada spec: 

npx cypress run --spec "cypress/e2e/login.cy.js"

12. Workflow completo

Agora podemos combinar todas as etapas estudadas. 

name: Cypress Tests

on:
push:
pull_request:

jobs:

cypress:

runs-on: ubuntu-latest

steps:

  - name: Checkout
    uses: actions/checkout@v4

  - name: Setup Node
    uses: actions/setup-node@v4
    with:
      node-version: 20

  - name: Install dependencies
    run: npm ci

  - name: Run Cypress
    run: npx cypress run

Esse workflow representa uma estrutura básica para executar testes Cypress em um pipeline de integração contínua.

13. Utilizando uma Action para o Cypress

Além de executar comandos diretamente com npx cypress run, também podemos utilizar uma action específica para o Cypress.

Um exemplo é: 

- name: Cypress run

uses: cypress-io/github-action@v6

A action pode cuidar de etapas comuns relacionadas à execução do Cypress.

Uma configuração simples pode ser: 

name: Cypress Tests

on:
push:
pull_request:

jobs:

cypress:

runs-on: ubuntu-latest

steps:

  - name: Checkout
    uses: actions/checkout@v4

  - name: Cypress run
    uses: cypress-io/github-action@v6

Actions reutilizáveis podem simplificar workflows ao encapsular tarefas recorrentes.

14. Executando apenas em determinadas branches

Podemos definir em quais branches determinados eventos devem iniciar o workflow.

Por exemplo: 

on:

push:

branches:
  - main

Nesse caso, o workflow será iniciado para pushes realizados na branch main.

Também podemos utilizar pull requests: 

on:

pull_request:

branches:
  - main

Filtros de branches permitem controlar em quais mudanças o pipeline será executado.

15. Executando o workflow manualmente

Podemos permitir que o workflow seja iniciado manualmente utilizando workflow_dispatch. 

on:

workflow_dispatch:

Podemos combinar execução manual com eventos automáticos: 

on:

push:

pull_request:

workflow_dispatch:

A execução manual pode ser útil para repetir um processo sem necessariamente realizar um novo commit.

16. Utilizando variáveis de ambiente

Pipelines frequentemente precisam trabalhar com configurações diferentes dependendo do ambiente.

Podemos definir variáveis utilizando env. 

jobs:

cypress:

runs-on: ubuntu-latest

env:
  CYPRESS_baseUrl: https://exemplo.com

Os testes Cypress podem utilizar essa configuração durante a execução.

Variáveis de ambiente ajudam a separar configurações da lógica dos testes.

17. Trabalhando com Secrets

Informações sensíveis não devem ser armazenadas diretamente no arquivo YAML.

O GitHub permite armazenar informações protegidas utilizando Secrets.

Um secret pode ser acessado no workflow utilizando: 

${{ secrets.NOME_DO_SECRET }}

Por exemplo: 

env:

API_TOKEN: ${{ secrets.API_TOKEN }}
Boa prática:

Evite colocar senhas, tokens, chaves privadas ou credenciais diretamente no código do workflow.

18. Armazenando resultados dos testes

Em uma execução de CI, pode ser importante preservar arquivos gerados pelos testes.

Por exemplo:

  • Screenshots.
  • Vídeos.
  • Relatórios.
  • Logs.

O GitHub Actions permite armazenar esses arquivos como artifacts. 

- name: Upload screenshots

if: failure()

uses: actions/upload-artifact@v4

with:
name: cypress-screenshots
path: cypress/screenshots

Utilizar artifacts permite analisar evidências mesmo depois que a execução do job terminou.

19. Capturando evidências quando o teste falha

Uma estratégia comum é enviar screenshots somente quando os testes apresentarem falha. 

- name: Upload screenshots

if: failure()

uses: actions/upload-artifact@v4

with:
name: screenshots
path: cypress/screenshots

O if: failure() permite executar essa etapa quando uma etapa anterior do job falhar.

Essa estratégia ajuda a preservar evidências importantes sem necessariamente armazenar arquivos a cada execução.

20. Entendendo o resultado do pipeline

Depois que o workflow é executado, o GitHub apresenta o status de cada job e etapa.

✅

Sucesso

Todas as etapas concluíram sem falhas.

❌

Falha

Uma ou mais etapas do workflow falharam.

⏳

Em execução

O workflow ainda está processando as etapas.

⏸️

Cancelado

A execução foi interrompida antes da conclusão.

Boas práticas com GitHub Actions

📌

Fixe versões quando necessário

Evite depender de alterações inesperadas no ambiente de execução.

🔐

Proteja secrets

Não coloque credenciais ou tokens diretamente no arquivo do workflow.

🧪

Execute testes relevantes

Estruture o pipeline para validar aquilo que realmente precisa ser verificado.

📊

Preserve evidências

Utilize artifacts para armazenar screenshots, vídeos e relatórios quando necessário.

🧹

Mantenha o workflow simples

Evite adicionar etapas desnecessárias ao pipeline.

📝

Use nomes claros

Nomeie jobs e steps de forma que o pipeline seja fácil de entender.

Erros comuns

❌

YAML inválido

Indentação incorreta ou estrutura inválida no arquivo do workflow.

❌

Dependências não instaladas

Executar os testes antes de instalar as dependências do projeto.

❌

Node incompatível

Utilizar uma versão do Node incompatível com o projeto.

❌

Secret ausente

O workflow espera uma variável protegida que não foi configurada no repositório.

❌

Caminho incorreto

O workflow referencia arquivos ou diretórios que não existem no projeto.

Exemplo completo com evidências

Podemos combinar a execução do Cypress com o envio de screenshots em caso de falha: 

name: Cypress Tests

on:

push:

pull_request:

workflow_dispatch:

jobs:

cypress:

runs-on: ubuntu-latest

steps:

  - name: Checkout
    uses: actions/checkout@v4

  - name: Setup Node
    uses: actions/setup-node@v4
    with:
      node-version: 20

  - name: Install dependencies
    run: npm ci

  - name: Run Cypress
    run: npx cypress run

  - name: Upload screenshots
    if: failure()
    uses: actions/upload-artifact@v4
    with:
      name: cypress-screenshots
      path: cypress/screenshots

Esse exemplo reúne os principais conceitos apresentados nesta aula: eventos, job, runner, checkout, Node.js, dependências, execução do Cypress e armazenamento de evidências.
