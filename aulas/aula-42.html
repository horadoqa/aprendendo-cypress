Cypress no CI

Aprenda a preparar e executar testes Cypress em ambientes de integração contínua utilizando pipelines automatizados.

O que é CI?

CI significa Continuous Integration, ou Integração Contínua.

A ideia é automatizar processos que acontecem quando alterações são enviadas para um repositório de código.

Entre esses processos podem estar:

📦

Instalação

Instalação das dependências necessárias para executar o projeto.

🧪

Testes

Execução automatizada da suíte de testes.

🔍

Validação

Verificação automática dos resultados da aplicação.

🚦

Feedback

Retorno rápido indicando se o processo foi concluído com sucesso ou falhou.

1. Como funciona um pipeline de CI?

Um pipeline pode ser configurado para executar uma sequência de etapas automaticamente. 

Desenvolvedor
  ↓

git push
↓
Repositório
↓
Pipeline CI
↓
Instalação das dependências
↓
Build da aplicação
↓
Execução dos testes
↓
Resultado

O objetivo é transformar etapas manuais em processos automatizados e repetíveis.

2. Por que executar Cypress no CI?

Os testes automatizados podem ser executados sempre que novas alterações forem enviadas para o projeto.

Isso permite identificar problemas antes que uma alteração seja disponibilizada para outros ambientes.

⚡

Feedback rápido

Os resultados dos testes podem ser obtidos automaticamente após uma alteração.

🔁

Repetibilidade

O mesmo processo pode ser executado várias vezes de maneira consistente.

🛡️

Detecção de regressões

Testes podem identificar comportamentos que foram alterados involuntariamente.

🤖

Automação

A execução não depende de uma pessoa abrir o Cypress manualmente.

3. Preparando o package.json

Uma forma comum de preparar um projeto para CI é criar scripts no arquivo package.json. 

{
"scripts": {
    "cy:open": "cypress open",
    "cy:run": "cypress run"
}

}

Dessa forma, podemos executar os testes utilizando: 

npm run cy:run
Boa prática:

Scripts deixam os comandos padronizados e facilitam a execução tanto localmente quanto no ambiente de CI.

4. Cypress em modo headless

Em um ambiente de CI normalmente não existe uma interface gráfica disponível para abrir o Cypress.

Por isso, utilizamos a execução em modo headless. 

npx cypress run

Também podemos utilizar o script definido no package.json: 

npm run cy:run

O processo pode executar os testes sem exigir que um navegador seja aberto manualmente pelo usuário.

5. O que um ambiente de CI precisa?

Para executar uma suíte Cypress, o ambiente de CI precisa possuir os recursos necessários para instalar o projeto e executar os testes.

Recurso Função
Node.js Executar o projeto e os comandos do Cypress.
npm Instalar dependências e executar scripts.
Cypress Executar os testes automatizados.
Navegador Executar os cenários que dependem de um browser.
Aplicação Sistema que será validado pelos testes.

6. Instalando as dependências no CI

O pipeline precisa instalar as dependências antes de executar os testes. 

npm ci

O comando npm ci é frequentemente utilizado em ambientes automatizados quando o projeto possui um package-lock.json.

A instalação das dependências deve acontecer antes da execução dos testes.

8. Configurando a baseUrl

Quando os testes acessam uma aplicação web, podemos configurar a baseUrl para evitar repetir o endereço completo. 

const { defineConfig } = require('cypress')

module.exports = defineConfig({

e2e: {

    baseUrl: 'http://localhost:3000'

}

})

Dessa forma, o teste pode utilizar: 

cy.visit('/login')

Em vez de: 

cy.visit('http://localhost:3000/login')

A configuração da URL base facilita a execução em diferentes ambientes.

9. Variáveis de ambiente

Ambientes de desenvolvimento, homologação e CI podem utilizar diferentes configurações.

Para valores que variam entre ambientes, podemos utilizar variáveis de ambiente e configurações apropriadas ao pipeline.

Por exemplo: 

TEST_USER_EMAIL

TEST_USER_PASSWORD
API_URL
Atenção:

Informações sensíveis não devem ser colocadas diretamente no código ou publicadas em arquivos versionados.

Ambientes de CI normalmente oferecem mecanismos próprios para armazenar secrets e variáveis protegidas.

10. Iniciando a aplicação antes dos testes

Se o Cypress precisa acessar uma aplicação local, o pipeline precisa garantir que ela esteja disponível antes da execução dos testes.

Um fluxo simplificado pode ser: 

npm ci

npm run build

npm run start

npm run cy:run

Em projetos reais, a forma de iniciar a aplicação depende da tecnologia utilizada e da configuração do pipeline.

O ponto principal é garantir que a aplicação esteja pronta para receber as requisições antes que os testes sejam iniciados.

11. Exemplo de pipeline

Podemos representar um pipeline de testes Cypress de forma simplificada: 

pipeline:

checkout

instalar dependências

iniciar aplicação

executar Cypress

coletar resultados

finalizar

Cada plataforma de CI possui sua própria sintaxe, mas o conceito geral permanece semelhante.

Primeiro entendemos o fluxo. Depois podemos adaptar esse fluxo para ferramentas específicas, como GitHub Actions.

12. O status do teste influencia o pipeline

Um dos pontos importantes da integração contínua é o código de saída do processo de testes.

Quando os testes são executados pelo comando: 

npx cypress run

o processo informa ao ambiente de execução se a execução terminou com sucesso ou apresentou falhas.

✅

Testes aprovados

A execução pode prosseguir para as próximas etapas do pipeline.

❌

Testes falhando

O pipeline pode sinalizar a falha para investigação da equipe.

13. Evidências de uma execução

Quando um teste falha no CI, é importante possuir informações suficientes para investigar o problema.

Dependendo da configuração, podemos trabalhar com recursos como:

📸

Screenshots

Capturas da interface no momento de uma falha.

🎥

Vídeos

Gravações da execução dos testes quando configuradas para esse objetivo.

📋

Logs

Informações da execução que ajudam na investigação do problema.

📊

Relatórios

Resultados consolidados da execução da suíte.

14. Exemplo de fluxo completo

Imagine um projeto com a seguinte configuração: 

curso-cypress/

├── cypress/
│
├── e2e/
│ ├── login.cy.js
│ └── cadastro.cy.js
│
├── fixtures/
│ └── usuario.json
│
├── support/
│
├── cypress.config.js
├── package.json
└── package-lock.json

O pipeline pode executar: 

npm ci

npm run cy:run

O Cypress então executará as specs configuradas e o ambiente de CI poderá utilizar o resultado para determinar o status daquela etapa.

O mesmo comando que funciona localmente pode fazer parte de um pipeline automatizado.

15. Executando localmente e no CI

É importante que a execução local e a execução no CI sejam previsíveis e próximas sempre que possível.

Local CI
Desenvolvedor executa o comando. Pipeline executa o comando.
Ambiente de desenvolvimento. Ambiente automatizado.
Resultado visualizado localmente. Resultado disponibilizado pelo pipeline.
Investigação imediata. Investigação baseada nos logs e evidências.

Boas práticas para Cypress no CI

⚙️

Padronize comandos

Utilize scripts do package.json para padronizar a execução dos testes.

🔐

Proteja secrets

Utilize mecanismos apropriados do CI para informações sensíveis.

🧪

Mantenha testes confiáveis

Evite testes instáveis que falham sem alterações reais no comportamento.

📊

Preserve evidências

Disponibilize logs, screenshots e outros resultados necessários para investigação.

⏱️

Controle o tempo

Organize a suíte para evitar execuções desnecessariamente demoradas.

🧹

Mantenha o ambiente previsível

Controle versões e dependências utilizadas durante a execução.

Erros comuns no CI

❌

Aplicação não iniciou

O Cypress tenta acessar uma aplicação que ainda não está disponível.

❌

Dependências ausentes

O pipeline tenta executar os testes sem instalar corretamente os pacotes.

❌

URL incorreta

A configuração aponta para um endereço que não existe no ambiente de CI.

❌

Secrets ausentes

O teste depende de uma variável que não foi configurada no ambiente.

❌

Testes instáveis

O mesmo cenário apresenta resultados diferentes sem uma alteração esperada.

❌

Evidências insuficientes

Uma falha acontece, mas não existem informações suficientes para investigá-la.
