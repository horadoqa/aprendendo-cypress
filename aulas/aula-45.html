1. O projeto

Durante o projeto final, vamos imaginar uma aplicação de e-commerce chamada QA Store.

A aplicação possui funcionalidades suficientes para criarmos diferentes cenários de automação.

🛒 Aplicação: QA Store

👤 Usuário: cadastro e autenticação

📦 Produtos: consulta e seleção de produtos

🛍️ Carrinho: inclusão e remoção de produtos

💳 Checkout: preenchimento dos dados da compra

✅ Pedido: confirmação da compra

2. Requisitos da suíte

Nossa suíte deverá cobrir os principais fluxos funcionais da aplicação.

4. Configurando o Cypress

Podemos configurar a URL principal da aplicação utilizando o baseUrl. 

const { defineConfig } = require('cypress')

module.exports = defineConfig({

    e2e: {

        baseUrl: 'http://localhost:3000'

    }

})

Dessa forma, os testes podem utilizar caminhos relativos: 

cy.visit('/login')

Centralizar a URL facilita a configuração do projeto e evita repetir o endereço completo em cada teste.

5. Criando a massa de dados

Vamos utilizar fixtures para separar os dados utilizados pelos testes.

Arquivo: 

cypress/fixtures/usuario.json
{
    "nome": "Maria",
    "email": "maria@teste.com",
    "senha": "123456"
}

Produto: 

{
    "nome": "Notebook",
    "preco": 3500
}

Fixtures permitem alterar os dados utilizados pelos cenários sem precisar modificar toda a lógica das specs.

6. Criando os testes de login

Vamos começar pela autenticação do usuário. 

describe('Login', () => {

    beforeEach(() => {

        cy.visit('/login')

    })

    it('deve realizar login com sucesso', () => {

        cy.fixture('usuario.json').then((usuario) => {

            cy.get('[data-testid="email"]')
                .type(usuario.email)

            cy.get('[data-testid="senha"]')
                .type(usuario.senha)

            cy.get('[data-testid="login"]')
                .click()

            cy.url()
                .should('include', 'dashboard')

        })

    })

})

Esse teste combina conceitos estudados em diversas aulas: fixtures, hooks, seletores, type(), click() e should().

7. Criando um cenário negativo

Uma suíte de qualidade não deve testar somente os caminhos de sucesso.

Também podemos verificar o comportamento da aplicação quando informações inválidas são utilizadas. 

it('deve exibir erro com senha inválida', () => {

    cy.get('[data-testid="email"]')
        .type('usuario@teste.com')

    cy.get('[data-testid="senha"]')
        .type('senha-incorreta')

    cy.get('[data-testid="login"]')
        .click()

    cy.get('[data-testid="mensagem-erro"]')
        .should('be.visible')

})

Testes negativos ajudam a verificar se a aplicação responde corretamente diante de entradas inválidas ou condições inesperadas.

8. Criando um Custom Command

Se vários testes precisarem realizar login, podemos criar um comando personalizado.

Arquivo: 

cypress/support/commands.js
Cypress.Commands.add('login', (email, senha) => {

    cy.visit('/login')

    cy.get('[data-testid="email"]')
        .type(email)

    cy.get('[data-testid="senha"]')
        .type(senha)

    cy.get('[data-testid="login"]')
        .click()

})

Agora o teste pode utilizar: 

cy.login(
    'usuario@teste.com',
    '123456'
)

Custom Commands são úteis para centralizar comportamentos que aparecem em diferentes testes.

9. Testando produtos

Depois da autenticação, podemos criar cenários relacionados aos produtos. 

describe('Produtos', () => {

    beforeEach(() => {

        cy.login(
            'usuario@teste.com',
            '123456'
        )

        cy.visit('/produtos')

    })

    it('deve exibir a lista de produtos', () => {

        cy.get('[data-testid="produto"]')
            .should('exist')

    })

})

Podemos também validar informações específicas: 

cy.get('[data-testid="produto-nome"]')
    .should('contain', 'Notebook')

cy.get('[data-testid="produto-preco"]')
    .should('be.visible')

10. Testando o carrinho

Agora vamos automatizar a inclusão de um produto no carrinho. 

it('deve adicionar produto ao carrinho', () => {

    cy.login(
        'usuario@teste.com',
        '123456'
    )

    cy.visit('/produtos')

    cy.get('[data-testid="adicionar-carrinho"]')
        .first()
        .click()

    cy.get('[data-testid="contador-carrinho"]')
        .should('contain', '1')

})

Observe a sequência do cenário:

Login → Produtos → Adicionar → Validar.

11. Testando o checkout

O checkout representa um fluxo E2E completo, envolvendo diferentes páginas e ações. 

it('deve finalizar uma compra', () => {

    cy.login(
        'usuario@teste.com',
        '123456'
    )

    cy.visit('/produtos')

    cy.get('[data-testid="adicionar-carrinho"]')
        .first()
        .click()

    cy.get('[data-testid="carrinho"]')
        .click()

    cy.get('[data-testid="checkout"]')
        .click()

    cy.get('[data-testid="nome"]')
        .type('Maria')

    cy.get('[data-testid="endereco"]')
        .type('Rua Cypress, 100')

    cy.get('[data-testid="finalizar"]')
        .click()

    cy.get('[data-testid="pedido-confirmado"]')
        .should('be.visible')

})

Esse é um exemplo de teste E2E porque valida uma jornada completa do usuário, desde a autenticação até a conclusão da compra.

12. Utilizando cy.intercept()

Também podemos controlar requisições durante os testes utilizando cy.intercept(). 

cy.intercept(
    'GET',
    '/api/produtos'
).as('listarProdutos')

cy.visit('/produtos')

cy.wait('@listarProdutos')
    .its('response.statusCode')
    .should('eq', 200)

Dessa maneira podemos sincronizar o teste com uma requisição específica e validar seu comportamento.

Interceptação é especialmente útil em cenários que dependem de APIs.

13. Adicionando um teste de API

Além dos testes E2E de interface, podemos utilizar o Cypress para validar endpoints diretamente. 

it('deve retornar produtos', () => {

    cy.request('GET', '/api/produtos')
        .then((response) => {

            expect(response.status)
                .to.eq(200)

            expect(response.body)
                .to.be.an('array')

        })

})

Assim, o projeto pode combinar testes de interface e testes de API em uma mesma estratégia de automação.

14. Organizando com Page Objects

Em projetos maiores, podemos encapsular elementos e comportamentos de uma página. 

class LoginPage {

    email = '[data-testid="email"]'

    senha = '[data-testid="senha"]'

    botaoLogin = '[data-testid="login"]'

    acessar() {

        cy.visit('/login')

    }

    preencherEmail(email) {

        cy.get(this.email)
            .type(email)

    }

    preencherSenha(senha) {

        cy.get(this.senha)
            .type(senha)

    }

    entrar() {

        cy.get(this.botaoLogin)
            .click()

    }

}

export default LoginPage

O teste pode então utilizar a classe: 

const loginPage = new LoginPage()

loginPage.acessar()

loginPage.preencherEmail('usuario@teste.com')

loginPage.preencherSenha('123456')

loginPage.entrar()

A organização deve ser adequada ao tamanho e às necessidades do projeto. O objetivo principal é facilitar manutenção e reutilização.

15. Separando dados da lógica

O projeto pode combinar fixtures e comandos personalizados. 

cy.fixture('usuario.json').then((usuario) => {

    cy.login(
        usuario.email,
        usuario.senha
    )

})

Dessa maneira, os dados ficam armazenados no fixture, enquanto o comportamento permanece na spec ou nos comandos reutilizáveis.

Dados → fixtures.

Comportamentos reutilizáveis → Custom Commands.

Cenários → Specs.

16. Criando assertions significativas

Um teste não deve apenas executar ações. Ele precisa verificar se o resultado esperado realmente aconteceu. 

cy.get('[data-testid="pedido-confirmado"]')
    .should('be.visible')

cy.get('[data-testid="numero-pedido"]')
    .should('not.be.empty')

cy.url()
    .should('include', 'pedido')
👀

Visibilidade

Verificar se um elemento está visível.

📝

Conteúdo

Validar textos e mensagens apresentadas.

🔗

URL

Validar a navegação realizada pelo usuário.

📡

Response

Validar status e dados retornados por APIs.

19. Executando o projeto

Para abrir a interface do Cypress: 

npx cypress open

Para executar os testes em modo headless: 

npx cypress run

Para executar uma spec específica: 

npx cypress run --spec 'cypress/e2e/login.cy.js'

A execução headless é especialmente útil em pipelines de CI/CD.

20. Executando no CI/CD

Depois que a suíte estiver funcionando localmente, podemos executá-la automaticamente em uma pipeline. 

name: Cypress Tests

on:

  push:

  pull_request:

jobs:

  cypress:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Instalar dependências
        run: npm ci

      - name: Executar Cypress
        run: npx cypress run

O pipeline pode ser expandido para armazenar screenshots, vídeos e relatórios como artefatos.
