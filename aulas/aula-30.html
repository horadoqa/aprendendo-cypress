O que é uma API?

API é a sigla para Application Programming Interface, ou Interface de Programação de Aplicações.

Uma API permite que diferentes sistemas ou partes de um sistema se comuniquem utilizando regras e formatos definidos.

Em uma aplicação web, por exemplo, o navegador pode enviar uma requisição para uma API para buscar, criar, alterar ou excluir informações. 

Aplicação

↓

Requisição HTTP

↓

API

↓

Banco de dados

↓

Resposta HTTP

🌐 API → permite a comunicação entre sistemas.

📤 Request → requisição enviada para a API.

📥 Response → resposta devolvida pela API.

1. Onde a API aparece em uma aplicação?

Em uma aplicação web, o usuário normalmente interage com a interface através do navegador.

Por trás dessa interface, o frontend pode realizar requisições para uma API. 

Usuário

↓
Frontend
↓
API
↓
Banco de dados

Por exemplo, quando um usuário realiza login, o frontend pode enviar uma requisição para uma API responsável pela autenticação. 

POST /login

A API processa os dados recebidos e retorna uma resposta. 

{
"token": "abc123",
"usuario": "Maria"

}

A interface é apenas uma das formas de consumir uma API. A API também pode ser acessada diretamente por outras aplicações e ferramentas de teste.

2. Request e Response

A comunicação HTTP normalmente envolve uma requisição e uma resposta.

📤

Request

É a requisição enviada pelo cliente para um servidor ou API.

📥

Response

É a resposta enviada pelo servidor depois de processar a requisição.

📍

Endpoint

É o endereço utilizado para acessar determinado recurso da API.

📦

Payload

São os dados enviados ou recebidos durante uma comunicação.

3. O que é um endpoint?

Um endpoint é uma URL utilizada para acessar determinado recurso disponibilizado por uma API.

Imagine uma API de usuários: 

https://api.exemplo.com/usuarios

Esse endpoint pode representar o recurso de usuários da aplicação.

Outros endpoints poderiam representar recursos diferentes: 

GET /usuarios

GET /produtos

GET /pedidos

POST /usuarios

O endpoint identifica o recurso que queremos consultar ou manipular através da API.

4. Métodos HTTP

As APIs utilizam métodos HTTP para indicar qual operação será realizada.

Método Objetivo Exemplo
GET Consultar informações. Buscar usuários.
POST Criar ou enviar um novo recurso. Criar usuário.
PUT Atualizar um recurso. Atualizar usuário.
PATCH Atualizar parcialmente um recurso. Alterar somente o e-mail.
DELETE Remover um recurso. Excluir usuário.

Os métodos HTTP ajudam a representar a intenção da requisição enviada para a API.

5. Método GET

O método GET é utilizado principalmente para consultar informações.

Um exemplo de requisição seria: 

GET /usuarios

A API poderia retornar uma lista de usuários: 

[
{
    "id": 1,
    "nome": "Maria"
},
{
    "id": 2,
    "nome": "João"
}

]

Em testes de API, podemos validar se a resposta possui os dados esperados.

🔎 GET → utilizado para consultar recursos.

6. Método POST

O método POST é utilizado para enviar dados ao servidor, frequentemente para criar um novo recurso. 

POST /usuarios

Podemos enviar um corpo contendo os dados: 

{
"nome": "Maria",
"email": "maria@teste.com"

}

A API pode processar essas informações e retornar o recurso criado: 

{
"id": 10,
"nome": "Maria",
"email": "maria@teste.com"

}

📨 POST → utilizado para enviar dados para a API, frequentemente para criação de recursos.

7. PUT, PATCH e DELETE

Além de GET e POST, APIs REST utilizam outros métodos para manipular recursos. 

PUT /usuarios/10

PATCH /usuarios/10

DELETE /usuarios/10
🔄

PUT

Normalmente utilizado para atualizar um recurso de forma mais completa.

✏️

PATCH

Normalmente utilizado para atualização parcial de um recurso.

🗑️

DELETE

Utilizado para solicitar a remoção de um recurso.

8. Códigos de status HTTP

A resposta de uma API possui um código de status que ajuda a indicar o resultado do processamento da requisição.

Status Categoria Exemplo
200 Sucesso. Requisição processada com sucesso.
201 Criado. Novo recurso criado.
204 Sem conteúdo. Operação concluída sem corpo de resposta.
400 Requisição inválida. Dados enviados de forma inválida.
401 Não autenticado. Credenciais ausentes ou inválidas.
403 Acesso proibido. Usuário não possui permissão.
404 Não encontrado. Recurso ou endpoint não encontrado.
500 Erro do servidor. Falha durante o processamento no servidor.

9. Headers HTTP

Headers são informações adicionais enviadas junto de uma requisição ou resposta HTTP.

Alguns headers comuns incluem: 

Content-Type: application/json

Authorization: Bearer token

Accept: application/json
📄

Content-Type

Indica o formato do conteúdo enviado ou recebido.

🔐

Authorization

Pode transportar informações utilizadas para autenticação e autorização.

📥

Accept

Indica formatos de resposta que o cliente espera receber.

10. Body da requisição

Algumas requisições HTTP possuem um corpo, conhecido como request body.

Ele pode conter os dados enviados para a API. 

{
"nome": "Maria",
"email": "maria@teste.com"

}

Em uma requisição POST, por exemplo, esses dados podem representar um novo usuário.

📦 Body → contém dados enviados no corpo da requisição quando o método e a API utilizam esse recurso.

11. Body da resposta

A resposta de uma API também pode possuir um corpo contendo informações para o cliente. 

{
"id": 10,
"nome": "Maria",
"email": "maria@teste.com"

}

Durante um teste, podemos validar se esses dados estão de acordo com o comportamento esperado. 

expect(response.body.nome)
.to.equal('Maria')

O corpo da resposta é uma das principais fontes de informações para validações em testes de API.

12. JSON e APIs

JSON é um formato muito utilizado para representar dados em APIs.

Um objeto JSON pode possuir propriedades e valores: 

{
"id": 1,
"nome": "Maria",
"ativo": true

}

Também podemos representar listas: 

[
{
    "id": 1,
    "nome": "Maria"
},
{
    "id": 2,
    "nome": "João"
}

]

No contexto de testes de API, é importante saber interpretar objetos e arrays JSON para validar corretamente as respostas.

13. O que podemos testar em uma API?

Um teste de API pode validar diferentes aspectos da comunicação entre cliente e servidor.

🔢

Status code

Verificar se a API retornou o código de status esperado.

📦

Response body

Validar os dados retornados pela API.

📋

Headers

Verificar informações presentes nos headers da resposta.

⚠️

Cenários de erro

Validar o comportamento da API diante de entradas inválidas ou não autorizadas.

14. Teste de API x Teste E2E

Testes E2E normalmente simulam a utilização da aplicação através da interface.

Já um teste de API pode realizar a comunicação diretamente com o serviço.

Característica Teste E2E Teste de API
Interface Normalmente utiliza a interface. Não depende da interface para realizar a requisição.
Comunicação Pode envolver frontend e backend. Comunicação direta com a API.
Validação Comportamento da aplicação. Requisição e resposta.
Exemplo Realizar login pela tela. Enviar requisição para endpoint de login.

Os dois tipos de teste podem fazer parte de uma estratégia de automação, cada um validando diferentes camadas da aplicação.

15. Por que testar APIs?

⚡

Testes mais diretos

É possível validar serviços sem depender de toda a interação pela interface.

🎯

Validar regras

Regras de negócio podem ser verificadas diretamente através das respostas da API.

🔍

Encontrar problemas

Falhas na comunicação entre sistemas podem ser identificadas através das requisições.

🔄

Combinar estratégias

Testes de API podem complementar testes de interface e testes E2E.

16. Testando APIs com Cypress

O Cypress possui recursos para realizar requisições HTTP diretamente durante os testes.

Um dos principais comandos utilizados para isso é: 

cy.request()

Por exemplo: 

cy.request('GET', '/usuarios')

Podemos então trabalhar com a resposta retornada pelo Cypress: 

cy.request('GET', '/usuarios')
.then((response) => {

    expect(response.status)
        .to.equal(200)

})

Na próxima aula vamos estudar o cy.request() em detalhes e criar nossas primeiras requisições HTTP diretamente pelo Cypress.

17. Exemplo completo de um teste de API

Considere uma API que disponibiliza o endpoint: 

GET /usuarios

Podemos criar um teste para verificar se a requisição foi processada com sucesso: 

describe('API de usuários', () => {

it('deve consultar usuários', () => {

    cy.request('GET', '/usuarios')
        .then((response) => {

            expect(response.status)
                .to.equal(200)

            expect(response.body)
                .to.exist

        })

})

})

Nesse exemplo, o teste verifica dois pontos: 

response.status

response.body

O objetivo aqui não é testar uma interface, mas validar diretamente o comportamento do serviço exposto pela API.

Boas práticas em testes de API

🎯

Tenha objetivos claros

Cada teste deve possuir uma finalidade bem definida.

🔎

Valide a resposta

Não se limite a verificar se a requisição foi enviada. Valide o resultado.

⚠️

Teste cenários negativos

Considere também entradas inválidas, autenticação e recursos inexistentes.

📁

Organize os testes

Utilize nomes claros e mantenha uma estrutura consistente para as specs.

Erros comuns ao iniciar testes de API

❌

Confundir endpoint e método

O endpoint identifica o recurso, enquanto o método HTTP representa a operação.

❌

Validar somente o status

Uma resposta com status esperado não significa necessariamente que todos os dados estejam corretos.

❌

Ignorar o body

O corpo da resposta pode conter informações importantes para a validação do cenário.

❌

Testar somente sucesso

APIs também precisam ser avaliadas em cenários de erro e entradas inválidas.
