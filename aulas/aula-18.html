AULA 18 • SHOULD()

should() no Cypress

Aprenda a utilizar o comando should() para criar asserções e validar elementos, textos, atributos, estados e comportamentos da aplicação.

Objetivos da aula

Nas aulas anteriores aprendemos a navegar pela aplicação, localizar elementos utilizando cy.get(), criar seletores e realizar interações com click() e type().

Agora vamos aprender uma das funcionalidades mais importantes do Cypress: as asserções.

✅

Criar asserções

Aprender como validar se o comportamento esperado realmente aconteceu.

👀

Validar elementos

Verificar se elementos estão visíveis, presentes ou em determinado estado.

📝

Validar conteúdo

Validar textos e informações apresentadas na interface.

🧪

Criar testes confiáveis

Transformar comportamentos esperados em validações automatizadas.

O que é uma assertion?

Uma assertion, ou asserção, é uma verificação realizada pelo teste para determinar se o resultado obtido corresponde ao resultado esperado.

Em outras palavras, podemos pensar em uma assertion como uma pergunta feita pelo teste:

❓ O elemento está visível?

❓ O texto está correto?

❓ O botão está habilitado?

❓ O campo contém o valor esperado?

❓ A aplicação apresentou o comportamento esperado?

Se a condição esperada for verdadeira, o teste continua. Caso contrário, o Cypress registra uma falha.

1. O que é o should()?

O should() é um comando utilizado para criar asserções sobre elementos e valores encontrados durante a execução do teste.

Sua estrutura básica é: 

cy.get('seletor')
.should('condição')

Por exemplo: 

cy.get('h1')
.should('be.visible')

Nesse caso, estamos dizendo ao Cypress:

O elemento h1 deve estar visível.

2. Estrutura do should()

O comando normalmente é utilizado após um comando que retorna ou localiza um elemento. 

cy.get('.login-button')
.should('be.visible')

Podemos interpretar o código da seguinte maneira:

🔎

cy.get()

Localiza o elemento que será validado.

➡️

.

Encadeia o próximo comando ao resultado anterior.

✅

should()

Define a condição que deverá ser verdadeira.

3. Validando visibilidade

Uma das asserções mais utilizadas é be.visible.

Ela verifica se o elemento está visível na página. 

cy.get('button')
.should('be.visible')

Podemos utilizar essa validação para garantir que elementos importantes da interface estão disponíveis para o usuário. 

cy.get('#login')
.should('be.visible')
Exemplo:

Se o botão de login deveria aparecer na tela, podemos validar sua visibilidade antes de continuar o teste.

4. Validando existência

A asserção exist verifica se o elemento existe no DOM. 

cy.get('.menu')
.should('exist')

É importante diferenciar existência de visibilidade.

Assertion O que verifica?
exist Verifica se o elemento existe no DOM.
be.visible Verifica se o elemento está visível.

5. Utilizando not

Podemos utilizar not para validar que uma determinada condição não é verdadeira.

Por exemplo: 

cy.get('.loading')
.should('not.be.visible')

Nesse caso, estamos verificando que o elemento de loading não está visível.

Outro exemplo: 

cy.get('.modal')
.should('not.exist')

O not pode ser utilizado para inverter determinadas condições de uma assertion.

6. Validando textos

Também podemos utilizar should() para verificar o conteúdo textual de um elemento.

Uma das formas mais comuns é utilizar contain. 

cy.get('h1')
.should('contain', 'Bem-vindo')

Nesse exemplo, o teste verifica se o elemento contém o texto informado.

Também podemos utilizar: 

cy.get('h1')
.should('have.text', 'Bem-vindo')
Assertion Objetivo
contain Verifica se o elemento contém determinado texto.
have.text Verifica o texto do elemento.

7. Validando classes

Podemos verificar se um elemento possui determinada classe CSS utilizando have.class. 

cy.get('.mensagem')
.should('have.class', 'sucesso')

Isso pode ser útil quando a aplicação utiliza classes para representar estados visuais.

Por exemplo: 

<div class="mensagem sucesso">
Cadastro realizado!

O teste poderia validar: 

cy.get('.mensagem')
.should('have.class', 'sucesso')

8. Validando atributos

O Cypress também permite verificar atributos presentes nos elementos.

Para isso, podemos utilizar have.attr. 

cy.get('a')
.should('have.attr', 'href')

Também podemos verificar o valor do atributo: 

cy.get('a')
.should(
    'have.attr',
    'href',
    '/produtos'
)

Isso é especialmente útil para validar links, atributos HTML e configurações específicas dos elementos.

9. Validando valores de campos

Para campos de formulário, podemos verificar o valor atual utilizando have.value. 

cy.get('#email')
.should('have.value', 'usuario@email.com')

Por exemplo, podemos preencher um campo: 

cy.get('#email')
.type('usuario@email.com')

E depois validar o valor: 

cy.get('#email')
.should('have.value', 'usuario@email.com')

Essa abordagem permite verificar se a interação com o formulário produziu o valor esperado.

10. Validando estados de elementos

Existem diversas assertions para verificar estados específicos dos elementos. 

cy.get('button')
.should('be.enabled')

Podemos verificar se um elemento está desabilitado: 

cy.get('button')
.should('be.disabled')

Também podemos verificar se um checkbox está marcado: 

cy.get('#termos')
.should('be.checked')
👁️

be.visible

Verifica se o elemento está visível.

🟢

be.enabled

Verifica se o elemento está habilitado.

🔴

be.disabled

Verifica se o elemento está desabilitado.

☑️

be.checked

Verifica se um checkbox ou radio está selecionado.

11. should() com argumentos

Algumas assertions recebem um segundo argumento para especificar o valor esperado.

Por exemplo: 

cy.get('h1')
.should('contain', 'Produtos')

Nesse caso:

contain → define o tipo de validação.

'Produtos' → define o valor esperado.

Outro exemplo: 

cy.get('input')
.should('have.value', 'Cypress')

12. Utilizando múltiplas assertions

Podemos realizar várias validações sobre o mesmo elemento. 

cy.get('button')
.should('be.visible')
.and('be.enabled')

Nesse exemplo, o botão precisa:

✅ Estar visível.

✅ Estar habilitado.

Também podemos utilizar and() para continuar uma cadeia de assertions. 

cy.get('button')
.should('be.visible')
.and('contain', 'Entrar')

13. Exemplo completo

Podemos combinar navegação, localização, interação e assertions em um mesmo teste. 

describe('Login', () => {

it('deve exibir a página de login', () => {

    cy.visit('/login')

    cy.get('h1')
        .should('be.visible')
        .and('contain', 'Login')

    cy.get('#email')
        .should('be.visible')
        .and('be.enabled')

    cy.get('#password')
        .should('be.visible')

    cy.get('button[type="submit"]')
        .should('be.visible')
        .and('be.enabled')

})

})

Esse teste não apenas interage com a página. Ele também verifica se a aplicação está apresentando os elementos esperados.

Ideia principal:

Um teste automatizado deve verificar resultados, e não apenas executar ações.

14. O Cypress espera automaticamente

Uma característica importante do Cypress é que suas assertions são automaticamente reavaliadas durante um período de tempo.

Por exemplo: 

cy.get('.resultado')
.should('be.visible')

Se o elemento ainda não estiver disponível imediatamente, o Cypress pode aguardar e tentar novamente até que a condição seja satisfeita ou o timeout seja atingido.

Importante:

Isso é diferente de simplesmente adicionar esperas fixas. O Cypress tenta sincronizar a execução do teste com o comportamento da aplicação.

15. Evite waits desnecessários

Um erro comum é utilizar esperas fixas para tentar resolver problemas de sincronização.

Por exemplo: 

cy.wait(5000)

cy.get('.resultado')
.should('be.visible')

Em muitos casos, podemos deixar a própria assertion verificar o estado esperado: 

cy.get('.resultado')
.should('be.visible')

Prefira esperar por uma condição observável da aplicação em vez de adicionar um tempo fixo sem necessidade.

16. should() com função

O should() também pode receber uma função para realizar validações mais específicas. 

cy.get('.produto')
.should(($elemento) => {

    expect($elemento).to.have.length(1)

})

Nesse formato, recebemos o elemento encontrado e podemos realizar verificações utilizando JavaScript e asserções do Chai.

Quando utilizar?

Esse formato pode ser útil quando uma validação não pode ser expressa facilmente utilizando uma assertion pronta.

Erros comuns ao utilizar should()

❌

Validar o elemento errado

Criar uma assertion sobre um elemento que não representa o comportamento realmente esperado.

❌

Usar texto excessivamente específico

Criar validações frágeis baseadas em textos que mudam frequentemente.

❌

Usar wait sem necessidade

Adicionar esperas fixas quando uma assertion poderia aguardar a condição correta.

❌

Validar apenas a existência

Verificar somente se um elemento existe quando o comportamento esperado exige uma validação mais específica.

Boas práticas com should()

🎯

Valide comportamentos importantes

Crie assertions que realmente comprovem o comportamento esperado da aplicação.

🔎

Utilize seletores confiáveis

Combine assertions com seletores estáveis para reduzir a fragilidade dos testes.

⏱️

Aproveite a espera automática

Prefira aguardar condições da aplicação em vez de utilizar waits fixos.

🧹

Mantenha as assertions claras

Escreva validações fáceis de entender e relacionadas ao comportamento esperado.
