AULA 32 • VALIDANDO RESPONSES

Validando Responses

Aprenda a validar status codes, headers e corpo das respostas HTTP utilizando o Cypress.

Objetivos da aula

Na aula anterior, aprendemos a utilizar o cy.request() para enviar requisições HTTP diretamente pelo Cypress.

Agora vamos aprender como analisar a resposta recebida pela API e criar validações para garantir que ela esteja de acordo com o comportamento esperado.

🔢

Validar status code

Verificar se a API retornou o código HTTP esperado.

📋

Validar headers

Verificar informações presentes nos headers da resposta.

📦

Validar body

Conferir os dados retornados no corpo da resposta.

🧪

Criar assertions

Utilizar asserções para verificar o resultado das requisições.

O que é uma response?

Quando uma aplicação envia uma requisição HTTP para uma API, o servidor processa essa requisição e retorna uma resposta.

Essa resposta normalmente possui informações como:

🔢

Status Code

Indica o resultado do processamento da requisição.

📋

Headers

Contêm metadados relacionados à resposta HTTP.

📦

Body

Contém os dados retornados pela API.

No Cypress, podemos acessar essas informações a partir do objeto retornado pelo cy.request().

1. Estrutura de uma response

Uma resposta recebida pelo Cypress pode ser trabalhada utilizando propriedades como status, headers e body. 

cy.request('GET', '/usuarios/1')
.then((response) => {

    cy.log(response.status)

    cy.log(response.headers)

    cy.log(response.body)

})

response.status → código HTTP retornado.

response.headers → headers enviados pelo servidor.

response.body → conteúdo retornado pela API.

2. Validando o status code

O status code é uma das primeiras informações que devemos validar em um teste de API.

Podemos verificar se uma requisição retornou 200, por exemplo: 

cy.request('GET', '/usuarios/1')
.then((response) => {

    expect(response.status)
        .to.equal(200)

})

Nesse caso, o teste espera que a API retorne o status HTTP 200.

Se a API retornar outro status, a assertion falhará e o teste será considerado como falho.

3. Principais status codes

Durante os testes de API, alguns códigos HTTP aparecem com bastante frequência.

Status Significado Exemplo
200 OK Requisição processada com sucesso.
201 Created Recurso criado com sucesso.
204 No Content Requisição processada sem conteúdo no corpo da resposta.
400 Bad Request Requisição inválida.
401 Unauthorized Requisição sem autenticação válida.
404 Not Found Recurso não encontrado.
500 Internal Server Error Erro interno no servidor.

4. Validando criação de recursos

Quando uma API cria um novo recurso, é comum que a resposta utilize o status 201. 

cy.request('POST', '/usuarios', {

nome: 'Maria',
email: 'maria@teste.com'

}).then((response) => {

expect(response.status)
    .to.equal(201)

})

Dessa forma, o teste verifica se a operação de criação retornou o código esperado.

5. Validando o body

Além do status code, podemos validar os dados retornados pela API.

Considere uma resposta como: 

{
"id": 1,
"nome": "Maria",
"email": "maria@teste.com"

}

Podemos validar propriedades específicas: 

cy.request('GET', '/usuarios/1')
.then((response) => {

    expect(response.body.nome)
        .to.equal('Maria')

    expect(response.body.email)
        .to.equal('maria@teste.com')

})

Não é necessário validar todo o body. Podemos validar somente as propriedades relevantes para o cenário.

6. Validando conteúdo com include

Podemos verificar se determinado valor está presente no retorno utilizando include. 

expect(response.body.nome)
.to.include('Maria')

Essa abordagem é útil quando não precisamos comparar exatamente todo o conteúdo de um campo.

Também podemos verificar se um objeto possui uma determinada propriedade: 

expect(response.body)
.to.have.property('email')

7. Validando propriedades

A assertion have.property permite verificar se determinada propriedade existe no objeto. 

expect(response.body)
.to.have.property('id')

expect(response.body)
.to.have.property('nome')

expect(response.body)
.to.have.property('email')
🔎

Verificar existência

Confirma se uma propriedade está presente no objeto retornado.

🎯

Validar conteúdo

Permite acessar a propriedade e verificar seu valor.

🧪

Criar cenários

Ajuda a verificar o contrato esperado da resposta.

8. Validando headers

Os headers carregam informações adicionais sobre a resposta HTTP.

Podemos acessar os headers através de: 

response.headers

Por exemplo: 

cy.request('GET', '/usuarios/1')
.then((response) => {

    expect(response.headers)
        .to.have.property('content-type')

})

Os nomes e valores dos headers dependem da API e da infraestrutura utilizada pelo servidor.

9. Validando Content-Type

APIs que retornam JSON normalmente informam o tipo de conteúdo através do header Content-Type. 

cy.request('GET', '/usuarios/1')
.then((response) => {

    expect(response.headers['content-type'])
        .to.include('application/json')

})

O include permite validar apenas a parte relevante do valor.

10. Criando múltiplas validações

Um mesmo teste pode validar diferentes partes da resposta. 

cy.request('GET', '/usuarios/1')
.then((response) => {

    expect(response.status)
        .to.equal(200)

    expect(response.headers)
        .to.have.property('content-type')

    expect(response.body)
        .to.have.property('id')

    expect(response.body.nome)
        .to.equal('Maria')

})

Dessa forma, o teste verifica status, headers e conteúdo da resposta em um único cenário.

11. Validando listas

APIs também podem retornar listas de objetos.

Exemplo: 

{
"usuarios": [
    {
        "id": 1,
        "nome": "Maria"
    },
    {
        "id": 2,
        "nome": "João"
    }
]

}

Podemos acessar itens específicos do array: 

expect(response.body.usuarios[0].nome)
.to.equal('Maria')

expect(response.body.usuarios[1].nome)
.to.equal('João')

Também podemos validar a quantidade de elementos: 

expect(response.body.usuarios)
.to.have.length(2)

12. Validando uma response completa

Podemos combinar diferentes assertions em um teste mais completo. 

describe('Usuários', () => {

it('deve retornar o usuário corretamente', () => {

    cy.request('GET', '/usuarios/1')
        .then((response) => {

            expect(response.status)
                .to.equal(200)

            expect(response.headers)
                .to.have.property('content-type')

            expect(response.body)
                .to.have.property('id')

            expect(response.body.id)
                .to.equal(1)

            expect(response.body.nome)
                .to.equal('Maria')

            expect(response.body.email)
                .to.equal('maria@teste.com')

        })

})

})

Esse tipo de teste verifica diferentes aspectos do contrato esperado pela API.

13. Validando cenários negativos

Testes de API também devem verificar situações em que a requisição não é válida ou o recurso não existe.

Por exemplo, podemos consultar um usuário inexistente: 

cy.request({
method: 'GET',
url: '/usuarios/9999',
failOnStatusCode: false

}).then((response) => {

expect(response.status)
    .to.equal(404)

})

Em cenários negativos, a API pode retornar um status de erro de propósito. A opção failOnStatusCode: false permite que o teste continue para que possamos validar essa resposta.

14. Validando mensagens de erro

Além do status HTTP, podemos validar informações presentes no body de uma resposta de erro. 

cy.request({
method: 'GET',
url: '/usuarios/9999',
failOnStatusCode: false

}).then((response) => {

expect(response.status)
    .to.equal(404)

expect(response.body.message)
    .to.equal('Usuário não encontrado')

})

Assim, o teste verifica tanto o código HTTP quanto a mensagem retornada pela API.

15. Validando resposta de um POST

Podemos aplicar os mesmos conceitos em requisições de criação. 

cy.request('POST', '/usuarios', {

nome: 'Maria',
email: 'maria@teste.com'

}).then((response) => {

expect(response.status)
    .to.equal(201)

expect(response.body)
    .to.have.property('id')

expect(response.body.nome)
    .to.equal('Maria')

expect(response.body.email)
    .to.equal('maria@teste.com')

})

O teste verifica se o recurso foi criado e se a API retornou os dados esperados.

16. Validando resposta de um PUT

O mesmo princípio pode ser utilizado para atualizações. 

cy.request('PUT', '/usuarios/1', {

nome: 'Maria Silva'

}).then((response) => {

expect(response.status)
    .to.equal(200)

expect(response.body.nome)
    .to.equal('Maria Silva')

})

Dessa maneira, verificamos se a alteração foi processada e retornou o valor esperado.

17. Validando resposta de um DELETE

Operações de exclusão também podem ser validadas. 

cy.request('DELETE', '/usuarios/1')
.then((response) => {

    expect(response.status)
        .to.equal(204)

})

Dependendo do contrato da API, a exclusão pode retornar 204 ou outro status definido pelo serviço.

O status esperado deve sempre refletir o contrato da API que está sendo testada.

18. Validando o contrato da API

Validar uma response significa verificar se a API está entregando aquilo que o teste espera.

🔢

Status

O código HTTP deve representar o resultado esperado da operação.

📋

Headers

Os metadados importantes devem estar presentes e possuir os valores esperados.

📦

Body

Os dados retornados devem possuir a estrutura e os valores esperados.

Boas práticas para validar responses

🎯

Valide o necessário

Concentre as assertions nas informações relevantes para o cenário.

📋

Conheça o contrato

Saiba quais status, headers e campos são esperados pela API.

❌

Teste erros

Inclua cenários negativos para verificar respostas de erro.

🧩

Evite excesso

Não transforme um teste simples em uma coleção de validações desnecessárias.

Erros comuns ao validar responses

❌

Status incorreto

Esperar um código HTTP que não corresponde ao contrato da API.

❌

Campo inexistente

Tentar acessar uma propriedade que não existe na resposta.

❌

Ignorar erros

Testar somente cenários de sucesso e não verificar respostas negativas.

❌

Assertions frágeis

Criar validações dependentes de informações que podem variar sem afetar o cenário.
