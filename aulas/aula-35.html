Interceptação na Prática

Aprenda a utilizar o cy.intercept() em cenários reais de testes E2E, controlando requisições, aguardando respostas e validando o comportamento da aplicação.

Objetivos da aula

Nas aulas anteriores, aprendemos a trabalhar com requisições HTTP, o comando cy.request() e a interceptação de chamadas utilizando cy.intercept().

Agora vamos combinar esses conhecimentos em cenários mais próximos de uma aplicação real.

O que significa interceptar uma requisição?

Quando uma aplicação web realiza uma chamada para uma API, o navegador envia uma requisição HTTP para um determinado endereço.

O Cypress pode observar essa comunicação e, dependendo do cenário, controlar o comportamento da requisição ou da resposta.

💡 A interceptação cria um ponto de controle entre a aplicação e as chamadas HTTP realizadas durante o teste.

1. Nosso cenário de teste

Imagine uma aplicação que possui uma página de usuários.

Ao acessar a página, o frontend realiza uma requisição: 

GET /api/usuarios

A API retorna uma lista de usuários: 

{
"usuarios": [
    {
        "id": 1,
        "nome": "Maria"
    },
    {
        "id": 2,
        "nome": "João"
    }
]

}

Nosso objetivo será interceptar essa requisição e observar o que acontece durante o carregamento da página.

2. Criando nosso primeiro cy.intercept()

Podemos interceptar todas as requisições que correspondem a uma determinada rota. 

cy.intercept('GET', '/api/usuarios')

Nesse exemplo informamos:

🌐

GET

O método HTTP que queremos observar.

🔗

/api/usuarios

A rota da API que será interceptada.

👀

Interceptação

O Cypress passa a observar chamadas compatíveis com essa definição.

3. Criando um alias para a requisição

Para facilitar a identificação da requisição, podemos criar um alias utilizando .as(). 

cy.intercept(
'GET',
'/api/usuarios'

).as('listarUsuarios')

Agora a requisição pode ser referenciada pelo nome: 

'@listarUsuarios'

🏷️ O alias funciona como um identificador que permite localizar aquela requisição durante o teste.

4. Aguardando a requisição com cy.wait()

Depois de criar um alias, podemos utilizar cy.wait() para aguardar que aquela requisição aconteça. 

cy.wait('@listarUsuarios')

Um cenário completo pode ser: 

cy.intercept(
'GET',
'/api/usuarios'

).as('listarUsuarios')

cy.visit('/usuarios')

cy.wait('@listarUsuarios')

⏳ Dessa forma, o teste espera especificamente pela requisição que recebeu o alias listarUsuarios.

5. Validando informações da requisição

O resultado de cy.wait() permite acessar informações da requisição e da resposta. 

cy.wait('@listarUsuarios').then((interception) => {

cy.log(interception.request.method)

cy.log(interception.request.url)

})

Podemos verificar, por exemplo, o método HTTP: 

expect(interception.request.method)
.to.equal('GET')

Também podemos validar a URL: 

expect(interception.request.url)
.to.include('/api/usuarios')

🔎 A interceptação permite verificar se a aplicação realmente realizou a chamada esperada.

6. Validando a resposta da API

Além da requisição, também podemos acessar informações da resposta. 

cy.wait('@listarUsuarios').then((interception) => {

expect(interception.response.statusCode)
    .to.equal(200)

})

Podemos também validar o corpo da resposta: 

cy.wait('@listarUsuarios').then((interception) => {

expect(interception.response.body)
    .to.have.property('usuarios')

})
📡

Request

Informações enviadas pela aplicação para a API.

📥

Response

Informações retornadas pela API.

✅

Assertion

Validações realizadas sobre a comunicação.

7. Primeiro teste completo

Agora podemos juntar interceptação, navegação, espera e validação. 

describe('Usuários', () => {

it('deve carregar a lista de usuários', () => {

    cy.intercept(
        'GET',
        '/api/usuarios'
    ).as('listarUsuarios')

    cy.visit('/usuarios')

    cy.wait('@listarUsuarios')
        .its('response.statusCode')
        .should('eq', 200)

})

})

Esse padrão é muito comum em testes E2E: primeiro configuramos a interceptação, depois executamos a ação que dispara a chamada e finalmente aguardamos e validamos a resposta.

8. A importância da ordem

A interceptação deve ser configurada antes da ação que dispara a requisição.

O padrão recomendado é: 

cy.intercept(...)

cy.visit(...)

cy.wait(...)

Evite configurar o intercept depois de executar a ação que dispara a requisição: 

cy.visit('/usuarios')

cy.intercept(
'GET',
'/api/usuarios'
)
Regra importante:

Configure a interceptação antes da ação que você espera observar.

9. Validando a interface após a resposta

A interceptação também pode ser utilizada para sincronizar a validação da API com a interface. 

cy.intercept(
'GET',
'/api/usuarios'

).as('listarUsuarios')

cy.visit('/usuarios')

cy.wait('@listarUsuarios')

cy.get('[data-testid="lista-usuarios"]')
.should('be.visible')

Nesse cenário temos duas validações:

🌐

API

A requisição foi realizada e retornou corretamente.

🖥️

Interface

A aplicação apresentou o resultado esperado para o usuário.

10. Validando o corpo da requisição

Em requisições como POST, PUT ou PATCH, podemos verificar os dados enviados pela aplicação. 

cy.intercept(
'POST',
'/api/usuarios'

).as('criarUsuario')

cy.get('#nome')
.type('Maria')

cy.get('#email')
.type('maria@teste.com')

cy.get('#salvar')
.click()

cy.wait('@criarUsuario')
.then((interception) => {

    expect(interception.request.body.nome)
        .to.equal('Maria')

    expect(interception.request.body.email)
        .to.equal('maria@teste.com')

})

📤 Esse tipo de validação permite verificar se a aplicação enviou corretamente os dados preenchidos pelo usuário.

11. Validando o corpo da resposta

Também podemos validar os dados retornados pela API. 

cy.wait('@criarUsuario')
.then((interception) => {

    expect(interception.response.body)
        .to.have.property('id')

    expect(interception.response.body.nome)
        .to.equal('Maria')

})

Dessa forma, o teste pode validar tanto a comunicação quanto o comportamento apresentado pela aplicação.

💡 Quando o cenário exige validação da API, não é necessário limitar o teste apenas aos elementos visuais da página.

12. Simulando uma resposta

O cy.intercept() também pode controlar a resposta recebida pela aplicação.

Por exemplo, podemos simular uma lista de usuários: 

cy.intercept(
'GET',
'/api/usuarios',
{
    statusCode: 200,
    body: {
        usuarios: [
            {
                id: 1,
                nome: 'Maria'
            }
        ]
    }
}

).as('listarUsuarios')

A aplicação receberá essa resposta durante o teste.

🧪 Essa técnica permite criar cenários previsíveis sem depender exclusivamente dos dados reais do ambiente.

13. Testando cenários de erro

Uma das aplicações mais úteis da interceptação é testar como a interface reage quando uma API retorna um erro.

Podemos simular, por exemplo, um erro HTTP 500: 

cy.intercept(
'GET',
'/api/usuarios',
{
    statusCode: 500,
    body: {
        mensagem: 'Erro interno do servidor'
    }
}

).as('erroUsuarios')

Depois podemos validar a mensagem exibida na tela: 

cy.visit('/usuarios')

cy.wait('@erroUsuarios')

cy.get('[data-testid="mensagem-erro"]')
.should(
'contain',
'Erro ao carregar usuários'
)
⚠️

API indisponível

Simule uma falha no servidor.

🧪

Interceptação

Controle a resposta recebida pela aplicação.

🖥️

Comportamento da UI

Verifique se a aplicação trata o erro corretamente.

14. Testando estados de carregamento

Interceptações também podem ajudar a testar comportamentos relacionados ao carregamento de dados. 

cy.intercept(
'GET',
'/api/usuarios'

).as('listarUsuarios')

cy.visit('/usuarios')

cy.get('[data-testid="loading"]')
.should('be.visible')

cy.wait('@listarUsuarios')

Podemos então validar que o estado de carregamento foi substituído pelo conteúdo final. 

cy.get('[data-testid="lista-usuarios"]')
.should('be.visible')

⏳ O teste pode acompanhar a transição entre diferentes estados da interface.

15. Trabalhando com múltiplos intercepts

Uma página pode realizar várias chamadas de API. Podemos criar aliases diferentes para cada uma. 

cy.intercept(
'GET',
'/api/usuarios'

).as('usuarios')

cy.intercept(
'GET',
'/api/produtos'
).as('produtos')

cy.visit('/dashboard')

cy.wait('@usuarios')

cy.wait('@produtos')

Cada chamada possui seu próprio identificador.

🏷️ Utilize aliases descritivos para deixar o teste fácil de entender e manter.

16. Exemplo prático: login

Vamos considerar uma aplicação que envia uma requisição POST para realizar o login. 

cy.intercept(
'POST',
'/api/login'

).as('login')

cy.visit('/login')

cy.get('#email')
.type('usuario@teste.com')

cy.get('#senha')
.type('123456')

cy.get('#login')
.click()

cy.wait('@login')
.then((interception) => {

    expect(interception.response.statusCode)
        .to.equal(200)

})

Podemos complementar o teste validando a navegação: 

cy.url()
.should('include', 'dashboard')

O cenário agora valida a interação do usuário, a requisição de login, a resposta da API e o resultado apresentado pela aplicação.

17. Exemplo prático: login inválido

Podemos utilizar interceptação para simular uma resposta de credenciais inválidas. 

cy.intercept(
'POST',
'/api/login',
{
    statusCode: 401,
    body: {
        mensagem: 'Credenciais inválidas'
    }
}

).as('loginInvalido')

Depois executamos o login: 

cy.get('#email')
.type('usuario@teste.com')

cy.get('#senha')
.type('senha-incorreta')

cy.get('#login')
.click()

cy.wait('@loginInvalido')

Finalmente, validamos a mensagem: 

cy.get('[data-testid="erro-login"]')
.should(
    'contain',
    'Credenciais inválidas'
)

18. Fluxo recomendado

1️⃣ Interceptar → configure o cy.intercept().

2️⃣ Nomear → crie um alias com as().

3️⃣ Executar → realize a ação que dispara a requisição.

4️⃣ Aguardar → utilize cy.wait().

5️⃣ Validar → verifique request, response e interface. 

cy.intercept(...)
.as('minhaRequisicao')

cy.visit(...)

cy.wait('@minhaRequisicao')

cy.get(...)
.should(...)

Boas práticas com cy.intercept()

🏷️

Use aliases claros

Escolha nomes que expliquem qual requisição está sendo interceptada.

🎯

Intercepte o necessário

Evite interceptações genéricas quando uma rota específica for suficiente.

⏳

Prefira esperar pela requisição

Utilize aliases e cy.wait() para sincronizar o teste com eventos reais da aplicação.

🧪

Valide o comportamento

Não limite o teste à interceptação: valide também o resultado apresentado pela aplicação.

Erros comuns

❌

Interceptar tarde demais

Configurar o intercept depois da ação que já disparou a requisição.

❌

Rota incorreta

Utilizar uma URL ou método HTTP diferente daquele realizado pela aplicação.

❌

Alias incorreto

Utilizar em cy.wait() um alias diferente do configurado no intercept.

❌

Validar somente a API

Ignorar o comportamento da interface após receber a resposta.

Exemplo completo

Vamos reunir os principais conceitos em um cenário de carregamento de usuários. 

describe('Lista de usuários', () => {

it('deve carregar os usuários corretamente', () => {

    cy.intercept(
        'GET',
        '/api/usuarios'
    ).as('listarUsuarios')

    cy.visit('/usuarios')

    cy.wait('@listarUsuarios')
        .then((interception) => {

            expect(interception.request.method)
                .to.equal('GET')

            expect(interception.request.url)
                .to.include('/api/usuarios')

            expect(interception.response.statusCode)
                .to.equal(200)

        })

    cy.get('[data-testid="lista-usuarios"]')
        .should('be.visible')

})

})

Esse teste valida a comunicação entre frontend e API e também verifica o resultado apresentado na interface.
