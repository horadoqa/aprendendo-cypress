AULA 33 • CY.INTERCEPT()

cy.intercept()

Aprenda a interceptar, observar, modificar e controlar requisições HTTP durante a execução dos testes com Cypress.

Objetivos da aula

Na aula anterior, aprendemos a validar respostas de APIs utilizando status codes, headers e corpo das respostas.

Agora vamos aprender como utilizar o cy.intercept() para observar e controlar requisições realizadas pela aplicação durante os testes.

👀

Observar requisições

Identificar e acompanhar requisições HTTP realizadas pela aplicação.

🏷️

Criar aliases

Nomear interceptações para aguardar e validar requisições específicas.

🎭

Simular respostas

Controlar a resposta da API utilizando dados definidos pelo próprio teste.

🧪

Testar cenários

Criar testes previsíveis para diferentes comportamentos da aplicação.

O que é cy.intercept()?

O cy.intercept() é um comando do Cypress utilizado para observar e controlar requisições e respostas HTTP realizadas pela aplicação.

Ele pode ser utilizado para monitorar uma requisição, esperar que ela seja concluída, modificar sua resposta ou fornecer uma resposta simulada. 

cy.intercept('GET', '/api/usuarios')

👀 Interceptar → observar uma requisição realizada pela aplicação.

🏷️ Alias → identificar uma interceptação durante o teste.

🎭 Stub → substituir ou controlar a resposta original.

🧪 Teste → validar o comportamento da aplicação diante daquela comunicação.

1. Sintaxe básica

A forma mais simples de utilizar o cy.intercept() é informar o método HTTP e a URL que desejamos observar. 

cy.intercept(
'GET',
'/api/usuarios'

)

Nesse exemplo, o Cypress passa a observar requisições GET realizadas para: 

/api/usuarios

O cy.intercept() deve ser configurado antes da ação que dispara a requisição que queremos observar.

2. Interceptando diferentes métodos HTTP

Podemos informar diferentes métodos HTTP no cy.intercept(). 

cy.intercept('GET', '/api/usuarios')

cy.intercept('POST', '/api/usuarios')

cy.intercept('PUT', '/api/usuarios/1')

cy.intercept('DELETE', '/api/usuarios/1')
📥

GET

Normalmente utilizado para consultar dados de uma API.

➕

POST

Normalmente utilizado para criar novos recursos.

✏️

PUT

Normalmente utilizado para atualizar recursos.

🗑️

DELETE

Normalmente utilizado para remover recursos.

3. Interceptando uma URL

Podemos informar diretamente a rota que queremos observar. 

cy.intercept(
'GET',
'/api/produtos'

)

Quando a aplicação realizar uma requisição compatível com essa rota, o Cypress poderá capturar essa comunicação.

O padrão utilizado na URL deve corresponder à requisição realizada pela aplicação.

4. Criando um alias

Podemos utilizar .as() para atribuir um nome à interceptação. 

cy.intercept(
'GET',
'/api/usuarios'

).as('buscarUsuarios')

Agora a interceptação pode ser referenciada utilizando o alias: 

'@buscarUsuarios'

Aliases tornam os testes mais legíveis e facilitam a identificação das requisições que estão sendo observadas.

5. Utilizando cy.wait()

Depois de criar um alias, podemos utilizar cy.wait() para aguardar que a requisição seja concluída. 

cy.intercept(
'GET',
'/api/usuarios'

).as('buscarUsuarios')

cy.visit('/usuarios')

cy.wait('@buscarUsuarios')

Nesse cenário, o Cypress aguarda a requisição associada ao alias antes de continuar para o próximo comando.

Boa prática:

Utilize aliases específicos para deixar claro qual comunicação o teste está aguardando.

6. Validando a requisição

O resultado retornado pelo cy.wait() pode ser utilizado para validar informações da requisição. 

cy.intercept(
'POST',
'/api/login'

).as('login')

cy.get('#login')
.click()

cy.wait('@login')
.its('request.body.email')
.should('eq', 'usuario@teste.com')

Podemos verificar informações como: 

request.method

request.url

request.body

request.headers
🌐

URL

Verificar para qual endereço a requisição foi enviada.

📦

Body

Validar os dados enviados para a API.

📋

Headers

Validar informações presentes nos cabeçalhos da requisição.

7. Validando a resposta

Além da requisição, também podemos validar a resposta recebida da API. 

cy.intercept(
'GET',
'/api/usuarios'

).as('usuarios')

cy.visit('/usuarios')

cy.wait('@usuarios')
.its('response.statusCode')
.should('eq', 200)

Também podemos acessar o corpo da resposta: 

cy.wait('@usuarios')
.its('response.body')

A interceptação permite analisar tanto o que a aplicação enviou quanto o que recebeu.

8. Request x Response

Uma interceptação pode fornecer informações sobre os dois lados da comunicação HTTP.

Objeto Informação Exemplo
request Método HTTP POST
request URL /api/login
request Body E-mail e senha
response Status code 200
response Body Dados retornados pela API

9. Utilizando padrões de URL

Podemos utilizar padrões para interceptar diferentes URLs que pertencem a uma mesma rota. 

cy.intercept(
'GET',
'/api/usuarios/*'

).as('usuario')

Outra possibilidade é utilizar curingas para trabalhar com diferentes partes de uma URL. 

cy.intercept(
'GET',
'**/api/usuarios/**'

)

Padrões de URL podem ser úteis quando a aplicação utiliza identificadores dinâmicos nas rotas.

10. Interceptando requisições com parâmetros

Uma aplicação pode enviar parâmetros na URL. 

/api/produtos?categoria=notebook

Podemos interceptar a rota utilizando um padrão compatível com a requisição. 

cy.intercept(
'GET',
'/api/produtos*'

).as('produtos')

Depois podemos aguardar a requisição: 

cy.wait('@produtos')

Em cenários mais específicos, podemos utilizar matchers para controlar exatamente quais requisições devem ser interceptadas.

11. Simulando uma resposta

Uma das funcionalidades mais importantes do cy.intercept() é permitir que o teste forneça uma resposta simulada. 

cy.intercept(
'GET',
'/api/usuarios',
{
    statusCode: 200,
    body: {
        usuarios: [
            {
                id: 1,
                nome: 'Maria'
            }
        ]
    }
}

)

Nesse caso, o teste define a resposta que será utilizada quando a requisição for interceptada.

Essa técnica é conhecida como stub ou simulação de resposta.

Ela permite testar comportamentos da interface sem depender do resultado real da API.

12. Simulando diferentes status codes

Podemos simular diferentes respostas HTTP para verificar como a aplicação reage a cada cenário.

Exemplo de sucesso: 

cy.intercept(
'GET',
'/api/usuarios',
{
    statusCode: 200,
    body: {
        usuarios: []
    }
}

)

Exemplo de erro: 

cy.intercept(
'GET',
'/api/usuarios',
{
    statusCode: 500,
    body: {
        mensagem: 'Erro interno do servidor'
    }
}

)
✅

200

Permite testar o comportamento esperado em uma resposta de sucesso.

🔐

401

Pode ser utilizado para testar cenários de autenticação.

🚫

403

Pode representar acesso não autorizado ao recurso.

💥

500

Permite testar o tratamento de erros do servidor.

13. Criando um mock de API

Podemos utilizar o intercept para criar um cenário completamente controlado pelo teste. 

cy.intercept(
'GET',
'/api/produtos',
{
    statusCode: 200,
    body: {
        produtos: [
            {
                id: 1,
                nome: 'Notebook',
                preco: 3500
            },
            {
                id: 2,
                nome: 'Mouse',
                preco: 150
            }
        ]
    }
}

).as('listarProdutos')

cy.visit('/produtos')

cy.wait('@listarProdutos')

A interface receberá os dados definidos pelo teste, independentemente dos dados disponíveis no ambiente real da API.

Mocks são especialmente úteis para reproduzir cenários específicos de teste.

14. Testando uma lista vazia

Podemos simular uma API que retorna uma lista vazia para verificar se a interface apresenta corretamente o estado de ausência de dados. 

cy.intercept(
'GET',
'/api/produtos',
{
    statusCode: 200,
    body: {
        produtos: []
    }
}

).as('produtos')

cy.visit('/produtos')

cy.wait('@produtos')

cy.contains('Nenhum produto encontrado')
.should('be.visible')

Esse tipo de cenário permite testar estados que podem ser difíceis de reproduzir utilizando apenas os dados reais da aplicação.

15. Testando mensagens de erro

Também podemos simular uma falha da API e verificar se a aplicação apresenta uma mensagem adequada. 

cy.intercept(
'GET',
'/api/produtos',
{
    statusCode: 500,
    body: {
        mensagem: 'Erro interno'
    }
}

).as('produtos')

cy.visit('/produtos')

cy.wait('@produtos')

cy.contains('Não foi possível carregar os produtos')
.should('be.visible')

O objetivo é validar o comportamento da interface quando a comunicação com o backend apresenta um problema.

16. Modificando a resposta

O intercept também pode ser utilizado para modificar informações antes que a resposta seja entregue ao código da aplicação. 

cy.intercept(
'GET',
'/api/usuarios',
(interception) => {

    interception.reply({
        statusCode: 200,
        body: {
            usuarios: [
                {
                    id: 1,
                    nome: 'Usuário de teste'
                }
            ]
        }
    })

}

)

Nesse cenário, o teste assume o controle da resposta que será entregue à aplicação.

Atenção:

Use essa abordagem de maneira consciente para que os testes continuem representando cenários relevantes da aplicação.

17. Inspecionando a requisição

Também podemos utilizar uma função para analisar informações da requisição. 

cy.intercept(
'POST',
'/api/login',
(req) => {

    console.log(req.body)

}

)

O objeto req representa a requisição interceptada. 

req.method

req.url

req.body

req.headers

Isso pode ser útil para compreender exatamente quais dados a aplicação está enviando ao backend.

18. Alterando dados da requisição

Em cenários específicos, também podemos modificar informações da requisição antes que ela continue seu fluxo. 

cy.intercept(
'POST',
'/api/login',
(req) => {

    req.body.email = 'teste@exemplo.com'

}

)

Dessa forma, o teste consegue controlar os dados enviados ao servidor.

Alterações de request devem ser utilizadas quando fizerem parte do objetivo do cenário de teste.

19. Configure o intercept antes da ação

Um ponto importante é configurar a interceptação antes de executar a ação que dispara a requisição.

Exemplo correto: 

cy.intercept(
'GET',
'/api/produtos'

).as('produtos')

cy.visit('/produtos')

cy.wait('@produtos')

Dessa forma, o Cypress já está observando a rota quando a aplicação realiza a requisição.

Boa prática:

Configure intercepts antes de executar cliques, navegações ou outras ações que possam disparar requisições.

20. Exemplo completo: login

Vamos combinar os conceitos estudados em um cenário de login. 

describe('Login', () => {

it('deve realizar login com sucesso', () => {

    cy.intercept(
        'POST',
        '/api/login'
    ).as('login')

    cy.visit('/login')

    cy.get('#email')
        .type('usuario@teste.com')

    cy.get('#senha')
        .type('123456')

    cy.get('#login')
        .click()

    cy.wait('@login')
        .its('response.statusCode')
        .should('eq', 200)

})

})

O teste executa a ação de login e aguarda explicitamente a comunicação com a API.

Dessa forma, podemos validar se a requisição ocorreu conforme esperado.

21. Exemplo completo com mock

Também podemos controlar completamente a resposta da API. 

cy.intercept(
'POST',
'/api/login',
{
    statusCode: 200,
    body: {
        token: 'token-teste',
        usuario: {
            nome: 'Maria'
        }
    }
}

).as('login')

cy.visit('/login')

cy.get('#email')
.type('usuario@teste.com')

cy.get('#senha')
.type('123456')

cy.get('#login')
.click()

cy.wait('@login')

cy.contains('Maria')
.should('be.visible')

Nesse exemplo, o teste não depende da resposta real do backend para validar o comportamento da interface.

22. Quando utilizar cy.intercept()?

👀

Observar chamadas

⏳

Aguardar APIs

Sincronizar o teste com uma requisição específica.

🎭

Criar mocks

Simular respostas para cenários específicos.

⚠️

Testar erros

Simular falhas e verificar o tratamento realizado pela interface.

23. cy.intercept() x cy.request()

Embora os dois comandos trabalhem com HTTP, eles possuem objetivos diferentes.

Comando Objetivo principal
cy.request() Enviar uma requisição HTTP diretamente pelo teste.
cy.intercept() Observar ou controlar requisições realizadas pela aplicação.

Pense em cy.request() como uma forma de realizar uma chamada HTTP diretamente.

Já o cy.intercept() permite observar e controlar a comunicação da aplicação.

Erros comuns ao utilizar cy.intercept()

❌

Interceptar depois da ação

Criar o intercept depois que a aplicação já realizou a requisição.

❌

URL incorreta

Utilizar uma rota que não corresponde à requisição real.

❌

Alias pouco claro

Utilizar nomes genéricos que dificultam entender qual requisição está sendo aguardada.

❌

Mock excessivo

Simular todas as respostas sem considerar quais cenários realmente precisam de controle.

Boas práticas com cy.intercept()

🎯

Use aliases claros

Escolha nomes que expliquem qual requisição está sendo interceptada.

⏱️

Intercepte antes

Configure o intercept antes da ação que dispara a requisição.

🧪

Valide o comportamento

Utilize interceptações para validar comunicação e comportamento da aplicação.

🎭

Use mocks com propósito

Simule respostas quando isso ajudar a reproduzir cenários importantes.
