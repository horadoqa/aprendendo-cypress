O que são Fixtures?

Fixtures são arquivos utilizados para armazenar dados que podem ser consumidos pelos testes.

Em vez de colocar todos os dados diretamente dentro dos testes, podemos armazená-los em arquivos separados.

📄 Fixture → arquivo que contém dados utilizados pelos testes.

🧪 Teste → utiliza esses dados durante a execução.

♻️ Reutilização → os mesmos dados podem ser utilizados em diferentes cenários.

1. O problema de colocar dados diretamente no teste

Imagine um teste de login contendo usuário e senha diretamente no código: 

describe('Login', () => {

it('deve realizar login', () => {

    cy.visit('/login')

    cy.get('[data-testid="email"]')
        .type('usuario@teste.com')

    cy.get('[data-testid="senha"]')
        .type('123456')

    cy.get('[data-testid="login"]')
        .click()

})

})

O teste funciona, mas os dados estão misturados com a lógica de automação.

Problema:

Conforme a quantidade de testes aumenta, manter usuários, produtos e outros dados diretamente no código pode deixar a suíte mais difícil de organizar.

2. Separando os dados do teste

Podemos criar um arquivo de fixture para armazenar os dados do usuário. 

cypress/

├── e2e/
│
├── fixtures/
│ └── usuario.json
│
└── support/

O arquivo usuario.json pode conter: 

{
"nome": "João",
"email": "usuario@teste.com",
"senha": "123456"

}

Agora os dados estão separados da implementação do teste.

O arquivo de teste fica responsável pela automação, enquanto a fixture fica responsável pelos dados.

3. A pasta cypress/fixtures

Por padrão, o Cypress utiliza a pasta cypress/fixtures para armazenar fixtures. 

cypress/

├── e2e/
│
├── fixtures/
│ ├── usuario.json
│ ├── produto.json
│ └── endereco.json
│
└── support/
👤

usuario.json

Pode armazenar dados relacionados a usuários utilizados nos testes.

🛒

produto.json

Pode armazenar informações sobre produtos.

📍

endereco.json

Pode armazenar informações utilizadas em formulários de endereço.

4. Trabalhando com arquivos JSON

Um dos formatos mais utilizados para fixtures no Cypress é o JSON.

Um arquivo JSON pode representar informações estruturadas: 

{
"nome": "Maria",
"email": "maria@teste.com",
"idade": 30

}

Também podemos utilizar objetos mais complexos: 

{
"usuario": {
    "nome": "Maria",
    "email": "maria@teste.com"
},

"endereco": {
    "cidade": "Rio de Janeiro",
    "estado": "RJ"
}

}

5. Utilizando cy.fixture()

O comando cy.fixture() permite carregar dados armazenados em uma fixture.

Por exemplo, considerando o arquivo: 

cypress/fixtures/usuario.json

Podemos carregá-lo utilizando: 

cy.fixture('usuario')

O Cypress procura o arquivo correspondente dentro da pasta de fixtures.

📁 fixtures/usuario.json → arquivo armazenado no projeto.

🧪 cy.fixture('usuario') → carrega os dados do arquivo.

6. Utilizando fixtures com alias

Podemos associar os dados carregados a um alias utilizando as(). 

cy.fixture('usuario')
.as('usuario')

Depois podemos utilizar o alias durante o teste. 

cy.get('@usuario')
Importante:

Aliases são úteis para compartilhar valores carregados durante o fluxo do teste.

7. Carregando uma fixture no beforeEach

Quando vários testes precisam dos mesmos dados, podemos carregar a fixture no hook beforeEach(). 

beforeEach(() => {

cy.fixture('usuario')
    .as('usuario')

})

Dessa forma, o carregamento acontece antes de cada teste.

Um exemplo completo: 

describe('Login', () => {

beforeEach(() => {

    cy.fixture('usuario')
        .as('usuario')

})

it('deve realizar login', function () {

    cy.visit('/login')

    cy.get('[data-testid="email"]')
        .type(this.usuario.email)

    cy.get('[data-testid="senha"]')
        .type(this.usuario.senha)

})

})

Perceba que utilizamos uma função tradicional no it() para acessar o alias através de this.

8. Atenção ao uso de this

Ao utilizar aliases com this, é importante observar a diferença entre uma função tradicional e uma arrow function.

Com função tradicional: 

it('deve utilizar os dados', function () {

cy.get('input')
    .type(this.usuario.email)

})

Nesse caso, o contexto fornecido pelo Cypress pode ser acessado através de this.

Evite fazer: 

it('deve utilizar os dados', () => {

cy.get('input')
    .type(this.usuario.email)

})
Boa prática:

Se precisar acessar aliases através de this, utilize uma função tradicional em vez de uma arrow function.

9. Exemplo completo: teste de login

Vamos criar uma fixture para um usuário: 

{
"email": "usuario@teste.com",
"senha": "123456"

}

Depois podemos utilizá-la no teste: 

describe('Login', () => {

beforeEach(() => {

    cy.fixture('usuario')
        .as('usuario')

})

it('deve realizar login com sucesso', function () {

    cy.visit('/login')

    cy.get('[data-testid="email"]')
        .type(this.usuario.email)

    cy.get('[data-testid="senha"]')
        .type(this.usuario.senha)

    cy.get('[data-testid="login"]')
        .click()

})

})

O teste agora utiliza os dados da fixture sem precisar armazenar email e senha diretamente na implementação.

10. Fixtures com listas de dados

Uma fixture também pode armazenar uma lista de objetos. 

[
{
    "nome": "Produto A",
    "preco": 100
},

{
    "nome": "Produto B",
    "preco": 200
},

{
    "nome": "Produto C",
    "preco": 300
}

]

Esse formato pode ser útil para cenários que precisam trabalhar com vários registros.

👤

Usuários

Diferentes usuários para diferentes cenários de teste.

📦

Produtos

Listas de produtos para validar catálogos e funcionalidades.

🧾

Pedidos

Dados estruturados para cenários de pedidos e compras.

11. Fixtures com objetos complexos

Podemos representar estruturas maiores dentro de uma única fixture. 

{
"cliente": {
    "nome": "Carlos",
    "email": "carlos@teste.com"
},

"pedido": {
    "numero": 12345,
    "status": "aprovado"
},

"produtos": [
    {
        "nome": "Produto A",
        "quantidade": 2
    }
]

}

Esse tipo de estrutura pode representar dados necessários para cenários mais completos.

12. Fixtures e manutenção dos testes

Uma das principais vantagens das fixtures é separar os dados da lógica de automação.

Imagine que vários testes utilizam o mesmo email. Se o email estiver em uma fixture, podemos alterar o valor em um único lugar.

Antes: 

teste A → usuario@teste.com

teste B → usuario@teste.com

teste C → usuario@teste.com

Com fixture: 

usuario.json
↓

teste A
teste B
teste C

Isso pode reduzir duplicação e facilitar a manutenção quando o mesmo conjunto de dados é realmente compartilhado entre diferentes testes.

13. Quando utilizar Fixtures?

Dados de usuários

🛒

Dados de produtos

📋

Dados previsíveis

Quando o teste precisa de informações estáveis e conhecidas.

♻️

Reutilização

Quando o mesmo conjunto de dados é utilizado em diferentes cenários.

14. Quando uma Fixture pode não ser suficiente?

Fixtures são úteis, mas não precisam ser utilizadas para absolutamente todos os dados dos testes.

Alguns cenários exigem dados dinâmicos, gerados durante a execução ou criados através da própria aplicação.

Exemplo:

Se cada teste precisa de um email único, simplesmente reutilizar o mesmo email de uma fixture pode não atender ao cenário.

Nesses casos, podemos utilizar estratégias de geração de dados ou criação de registros através de APIs e outras abordagens.

Boas práticas com Fixtures

📁

Organize os arquivos

Utilize nomes claros e mantenha as fixtures relacionadas organizadas.

🏷️

Use nomes descritivos

Prefira nomes como usuario.json e produto.json em vez de nomes genéricos.

🔐

Não armazene segredos

Evite colocar senhas reais, tokens ou outras informações sensíveis em arquivos versionados.

🎯

Use dados relevantes

Mantenha nas fixtures somente os dados necessários para os cenários.

♻️

Reutilize quando fizer sentido

Compartilhe dados quando isso tornar os testes mais simples e não criar dependências indesejadas.

🧹

Evite fixtures gigantes

Divida grandes conjuntos de dados quando isso melhorar a organização.

Erros comuns

❌

Dados desatualizados

Utilizar uma fixture que não representa mais o comportamento esperado pela aplicação.

❌

Fixture gigante

Colocar dados de muitos cenários diferentes em um único arquivo difícil de manter.

❌

Dados sensíveis

Armazenar credenciais reais ou tokens em arquivos que podem ser versionados.

❌

Reutilização excessiva

Forçar todos os testes a dependerem de uma única massa de dados mesmo quando os cenários são diferentes.
